# @bills/cloud-hub — облачная касса (прототип)

Проверка идеи: тот же HUB, что в пробной версии в браузере, но в облаке Cloudflare.
**Один Durable Object на кофейню**: у объекта своя база SQLite (`ctx.storage.sql`, синхронная,
как `node:sqlite`). Любой телефон или ПК открывает один и тот же сайт, один раз вводит
«Код кофейни», потом входит своим ключом сотрудника. Живые обновления идут по WebSocket
(Hibernation API): пока в кофейне ничего не происходит, объект спит и не стоит денег.

Это прототип в ветке. Ничего не задеплоено, ресурсов в Cloudflare и Supabase не создано.

## Как запустить локально

```
npm ci
npm run build:web -w @bills/cloud-hub   # экраны TS в режиме облака → apps/cloud-hub/web-dist
npm run dev -w @bills/cloud-hub         # wrangler dev на http://127.0.0.1:8790, ADMIN_TOKEN=local-admin
node apps/cloud-hub/scripts/e2e.mjs new # новая кофейня, два устройства, заказ, WebSocket
```

- Новая кофейня: `POST /admin/cafes` с `Authorization: Bearer <ADMIN_TOKEN>` и телом
  `{venue, managerName, withMenu?, timezone?}`. В ответе — код кофейни и ключ директора.
- Перенос пробной: `node scripts/make-trial-snapshot.ts <файл>`, потом
  `node scripts/e2e.mjs import <файл> <ключ>`. Это `POST /admin/cafes/import` с `{snapshot}`:
  base64 файла SQLite, ровно то, что пробная кладёт в Supabase `trials.snapshot`.
- В браузере: `http://127.0.0.1:8790/#/cafe/<код>`. Код запоминается, дальше обычный вход.
- Остальные режимы `e2e.mjs`:
  - `check <код> <ключ>` — после перезапуска данные на месте;
  - `load <код> <ключ> [n]` — сколько стоит заказ в единицах Cloudflare.

## Как устроено

```
телефон / ПК ──https──▶ Worker (worker.ts) ──▶ Durable Object «кофейня K7F3…» (cafe-hub.ts)
  экраны TS             /c/<код>/api/*           HUB целиком: apps/hub/src
  (static assets,       /c/<код>/api/events ═WS═▶ SQLite объекта (shims/sqlite.ts)
   бесплатно)           /admin/*                 MiniFastify.inject → маршруты HUB
```

| Часть | Файл | Что делает |
|---|---|---|
| Worker | `src/worker.ts`, `src/http.ts` | Маршрут `/c/<код>/…` к объекту кофейни. Неверный код — 404 ещё до объекта. Сам отвечает на CORS preflight. Ограничение размера: API 256 КБ, импорт 9 МБ (413). Отдаёт экраны TS. |
| Объект кофейни | `src/cafe-hub.ts` | Поднимает HUB на своей SQLite. Каждый `/api/*` идёт через `app.inject` в маршруты HUB: вход по ключам, сессии, троттлинг, права — всё родное. `/api/events` — WebSocket на Hibernation API. Событие HUB `changed` рассылается во все сокеты. На ping отвечает сам рантайм (`setWebSocketAutoResponse`), объект не просыпается. |
| `node:sqlite` | `src/shims/sqlite.ts` | DatabaseSync/StatementSync поверх `ctx.storage.sql`. Считает прочитанные и записанные строки — заголовок `x-ts-cost`. |
| Транзакции | `scripts/db-adapter.mjs` | Durable Object не принимает `BEGIN`/`COMMIT`. Сборка подменяет в `db.ts` эти две строки на `storage.transactionSync(fn)`. Если `db.ts` поменяется, упадут сборка и тест. |
| Таймеры HUB | `src/timers.ts` | Интервалы HUB не взводятся, а выполняются догоняющей работой в начале следующего запроса. Иначе объект не уснёт (128 МБ × 86 400 с ≈ 11 000 ГБ·с в сутки — почти весь бесплатный лимит на одну кофейню). |
| Миграции | `build.mjs` (`virtual:hub-migrations`), `src/shims/fs.ts` | SQL-миграции HUB вшиты в бандл. |
| Импорт пробной | `src/snapshot.ts` | sql.js (WebAssembly) открывает файл пробной. Таблицы, строки, индексы и счётчики копируются одной транзакцией объекта, потом догоняют новые миграции. Ключи сотрудников остаются прежними. |
| Экраны | `apps/web/src/cloud/*`, флаг `VITE_CLOUD_HUB=1` | Экран «Код кофейни». `HUB_URL = /c/<код>`. `EventSource('/api/events')` → WebSocket. В облаке опрос реже: список бариста и экран гостей раз в 30 с, состояние раз в 120 с. Обычные сборки этого кода не содержат. |

Экраны можно держать и на Cloudflare Pages: `VITE_CLOUD_HUB_URL=https://<worker>` плюс `ALLOWED_ORIGINS`.
Но выгоднее отдавать их тем же Worker'ом (`[assets]` в `wrangler.toml`): тот же адрес, нет CORS и
preflight, а запросы к статике бесплатны.

## Что доказано (wrangler 4.151.3 / workerd 1.20261019, локально)

- **Два устройства одновременно.** Это два разных origin в браузере (`127.0.0.1` и `localhost`),
  то есть отдельные сессии.
  - Касса: директор, ключ директора.
  - Планшет: бариста Дана, её собственный ключ, выданный через `/api/staff/:id/keys`.
  - На кассе пробили заказ «2× Чёрный» с оплатой наличными. Через 17 мс после «Принять» экран
    бариста получил событие по WebSocket и стал перечитывать данные. Через 345 мс заказ уже на
    экране. Опрос в облаке раз в 30 с, так что это именно WebSocket.
  - Скрипт: событие доходит за 17–25 мс, ping→pong автоответом — 2 мс.
- **Перезапуск.** После остановки и запуска `wrangler dev` (дважды) кофейни, заказы, смена и
  сессии на месте.
- **Импорт пробной.**
  - Файл 811 КБ, 48 таблиц, 770 строк, импорт за 188 мс.
  - Вход прежним ключом директора пробной.
  - Видно: меню из 13 позиций, 8 заказов дня, открытую смену №3 с 5 400 ₸ в кассе и очередь
    бариста (Дина, Тимур, Ерлан) — как в пробной.
- **Проверки и защита.**
  - Неизвестный или кривой код — 404 «Кофейня не найдена».
  - Тело больше 256 КБ — 413.
  - Без ключа — 401 от самого HUB.
  - `/admin` без токена — 401.
  - `/api/events` без upgrade — 426.
- **Тесты.** `npm test -w @bills/cloud-hub`, 12 тестов. Миграции HUB и `transaction()` HUB
  гоняются по правилам Durable Object через тот же патч; плюс маршруты, лимит тела, CORS, таймеры.

### Сколько стоит одна операция (измерено, заголовок `x-ts-cost`)

| Запрос | Строк прочитано | Строк записано | SQL |
|---|---|---|---|
| `POST /api/counter/orders` (заказ с оплатой, склад по рецептам) | ~214 | **~71** | ~118 |
| `POST /api/counter/orders/:id/stage` (×3 на заказ) | ~22 | ~10 | ~25 |
| `GET /api/state` | 67 + **~15 на каждый заказ смены** (707 при 43 заказах) | 0 | 25 |
| `GET /api/counter/orders` | 15 + ~5 на заказ дня | 0 | 11 |
| `POST /api/auth/login` | ~15 | ~12 | 22 |
| Подъём объекта после сна | ~22 | 0 | 10 |

- Время обработчика объекта локально, 860 запросов: 94% — до 5 мс, 98,7% — до 10 мс.
  Максимум 70–114 мс — холодный старт и импорт.
- Бандл: 827 КиБ JS + 669 КиБ wasm.
- Новая кофейня с примером меню занимает 0,68 МБ, после 43 заказов — 1,33 МБ.

| Хранение | 5 ГБ на аккаунт; на один объект 10 ГБ в таблице, но в FAQ сказано «1 ГБ на Free» (противоречие) | [pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/), [limits](https://developers.cloudflare.com/durable-objects/platform/limits/) |

Как считается оплата:
- Время работы DO считается по 128 МБ. Счётчик останавливается, когда объект может уснуть
  (после 10 с без событий). Ожидающие `setTimeout`/`setInterval` уснуть не дают
  ([lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)).
- Открытие WebSocket — 1 запрос. Входящие сообщения считаются 20:1. Исходящие и ping бесплатны.
  Пока объект спит, ГБ·с не идут ([websockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)).
  Автоответ на ping не будит объект и не тарифицируется ([state API](https://developers.cloudflare.com/durable-objects/api/state/)).
- Вызов Worker → DO оплачивается и как запрос Worker, и как запрос DO.
- Будильник (alarm) — запрос DO плюс 1 записанная строка.
- Статика бесплатна и не ограничена ([static assets](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)).

### Сколько кофеен влезет

Модели кофеен (12 часов работы в день):
- **Малая:** 150 заказов в день, 3 экрана — касса, бариста, экран гостей.
- **Средняя:** 400 заказов в день, 4 экрана.

Один заказ проходит путь «пробили → готовится → готов → выдан». Это 4 команды. Каждое событие
заставляет каждый экран перечитать `/api/state` и свой список. Выходит около 30 запросов к
объекту на заказ (на средней — около 36) и около 100 записанных строк.

| Free, в сутки | Малая сейчас | Малая после доработок | Средняя сейчас | Средняя после доработок |
|---|---|---|---|---|
| Запросы DO и Worker | ~8 100 → 12 кофеен | ~4 700 → 21 | ~18 400 → 5 | ~14 700 → 6 |
| Записано строк | ~19 500 → **5** | ~19 500 → **5** | ~46 000 → **2** | ~46 000 → **2** |
| Прочитано строк | ~3,2 млн → **1** | ~0,26 млн → 19 | ~12 млн → **0** | ~0,7 млн → 7 |
| ГБ·с | ~3 600 → **3** | ~850 → 15 | ~5 000 → 2 | ~2 300 → 5 |
| **Итого на Free** | **1 малая** | **~5 малых** | **0** | **~2 средних** |

«Доработки» — это две вещи:
1. `/api/state` не пересчитывает ожидаемую наличность по всему журналу смены на каждый вызов
   (`toShiftView` → `shiftTotals(shiftLedger)` в `views.ts`). Отсюда «+15 строк на заказ».
   Нужен счётчик в строке смены или кэш.
2. Страховочный опрос экранов раз в 10 минут вместо 30–120 с: каждое изменение и так приходит
   по WebSocket.

Без второго объект бодрствует бо́льшую часть рабочего дня.

**Paid $5**, после доработок, в месяц на кофейню:
- малая: ~141 тыс. запросов DO, ~25 тыс. ГБ·с, ~0,6 млн записанных строк;
- средняя: ~441 тыс. запросов, ~69 тыс. ГБ·с, ~1,4 млн строк.

Сколько это стоит:
- Сами $5 покрывают ~7 малых или ~2 средних кофейни. Узкое место — 1 млн запросов DO.
- 50 малых ≈ $17 в месяц, 100 малых ≈ $47, 100 средних ≈ $195. Дальше в основном платим за
  ГБ·с и записанные строки.
- Без доработок 100 малых кофеен дают ~$130 в месяц только за время работы объектов.

Хранение: по замеру ~5–15 КБ на заказ, малая кофейня — ~0,3–0,8 ГБ в год. Если на Free
действительно 1 ГБ на объект, через 1,5–3 года понадобится архив. На Paid лимит 10 ГБ.

## Где лежат данные

- Объект создаётся рядом с первым запросом и хранит данные там же
  ([data location](https://developers.cloudflare.com/durable-objects/reference/data-location/)).
- Юрисдикции есть только `eu`, `us`, `fedramp`. Хранилищ DO в Казахстане и Средней Азии нет:
  Алматы и Астана в списке мест, где DO не создаются
  ([where.durableobjects.live](https://where.durableobjects.live/region/eeur), неофициально).
- Запрос из Казахстана на практике приводит к созданию объекта во Франкфурте.
- Закон РК № 94-V «О персональных данных и их защите», ст. 12 п. 2: хранение персональных данных —
  «в базе … которые находятся на территории Республики Казахстан»
  ([adilet.zan.kz](https://adilet.zan.kz/rus/docs/Z1300000094)).
  - Ст. 16 разрешает трансграничную передачу, но не отменяет хранение в РК.
  - Штрафы — КоАП ст. 79, от 60 МРП (≈260 тыс. ₸, малый бизнес)
    ([КоАП](https://adilet.zan.kz/rus/docs/K1400000235)).
- В кофейне персональные данные — это имена сотрудников, IP и устройства входов, имена гостей на
  заказах, телефоны гостей в «Гостях» (лояльность).
- Значит, облачная касса на Cloudflare нарушает требование о хранении в РК так же, как Supabase.
  Об этом уже сказано в главном README. Нужен юрист.
- Варианты:
  - не хранить телефоны гостей в облаке;
  - держать основную копию в РК (VPS в Алматы с тем же HUB — это платно);
  - принять риск на пилот.

## Что сломается или потребует доработки

1. **Таймеры.** Интервалы HUB захвачены (`timers.ts`).
   - Кофейне они не нужны: лампы, «Сторож», предоплаченные игры, неявки по броням.
   - Бильярду в облаке понадобятся будильники DO на ближайший дедлайн (alarm = запрос + 1 строка).
   - `Hub.start()` повторён частично: без `lamps.recover()`, который на каждом старте пишет в
     журнал «hub.recovered». Если HUB добавит шаг в `start()`, облако его пропустит. Лучше дать
     HUB маленький флаг старта.
2. **Часы.** `Date.now()` в Workers не идёт внутри запроса, двигается только на вводе-выводе.
   Для HUB это нормально: время одно на всю команду, часы Cloudflare точнее часов кассового ПК.
   Рабочий день считается по `club.timezone`.
3. **Файлы, бэкапы, CLI.**
   - Диска нет. `ops.ts` (VACUUM INTO, отметки бэкапа), `cli.ts`, mDNS, TLS, мастер `/setup`,
     ИБП, лампы и sync в облаке не работают и не нужны.
   - Бэкап: у SQLite-объектов есть восстановление на любой момент за 30 дней (PITR, только в
     продакшене) ([sqlite-storage-api](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)).
   - Кнопка «Скачать копию» — это обратный импорт: таблицы через sql.js в файл того же формата,
     что у пробной. Не сделано.
4. **Лицензия.** Прототип подписывает себе лицензию dev-ключом, как пробная: его закрытая
   половина лежит в репозитории. До настоящих клиентов лицензии должен выдавать TS.
5. **Фискализация.** Будущий вызов Webkassa — это `fetch` из объекта, повторы очереди
   (`fiscal/queue.ts`, на таймерах) — через будильники.
6. **Безопасность.**
   - Код кофейни — это адрес, он попадает в URL и логи.
   - `/api/auth/roster` публичен: зная код, можно увидеть имена и роли сотрудников. В облаке его
     лучше выключить.
   - `/api/events` публичен, как в HUB: несёт только «что-то изменилось».
   - Троттлинг входа идёт по IP, а за NAT кофейни IP общий: неверные ключи с одного устройства
     блокируют всю кофейню. Лучше считать по устройству.
   - `/admin` закрыт одним токеном. В продакшене его вызывает платформа TS (функция Supabase при
     одобрении заявки).
7. **CPU на Free.**
   - Обычный запрос укладывается в 1–5 мс.
   - Холодный старт объекта (десятки мс) и импорт (~190 мс на 0,8 МБ) превышают 10 мс.
     «Гибкость» на редкие превышения есть, но импорт крупной пробной на Free может не пройти:
     делать его на Paid или по частям.
   - Проверить можно только деплоем.
8. **Переезд пробной.**
   1. TS одобряет заявку, платформа берёт свежий `trials.snapshot` (механизм «прислать копию»
      уже есть в `trial-move`) и вызывает `POST /admin/cafes/import`. Получается код кофейни.
   2. Касса пробной показывает «Касса переехала в облако: откройте сайт и введите код …» и
      становится только для чтения (как сигнал `moved` в `trial-move`).
   3. Каждое устройство один раз вводит код кофейни и входит прежним ключом.
   - Не сделано: экран «переехала» в пробной и связка с Supabase.
9. **Без интернета.**
   - Устройство без связи с облаком ничего не может: экраны показывают обычное «Нет связи с HUB».
     Команды уходят с Idempotency-Key, повтор безопасен.
   - Если кассе нужно работать офлайн:
     - простое решение — резервный мобильный интернет (раздача с телефона);
     - очередь продаж в браузере кассы (только оплаченные заказы, номер присваивается при
       отправке). Средняя работа, конфликты по складу и номерам надо продумать;
     - полноценная локальная копия HUB с синхронизацией в две стороны — дорого.
     - Решение за владельцем.
10. **Опросы экранов.** В облачной сборке они уже реже. Чтобы объект спал, страховочный опрос
    стоит опустить до 10 минут.

## Решения за владельцем
