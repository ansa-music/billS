# @bills/cloud-hub — облачная касса TS (Worker `ts-kassa`)

Тот же HUB, что в кассе на мини-ПК и в пробной версии в браузере, но в облаке Cloudflare.
**Один Durable Object на кофейню**: у объекта своя база SQLite (`ctx.storage.sql`, синхронная, как
`node:sqlite`). Любой телефон или ПК открывает один сайт, один раз вводит «Код кофейни» (или открывает
ссылку `/#/cafe/<код>`), потом входит своим ключом. Живые обновления идут по WebSocket (Hibernation API):
пока в кофейне ничего не происходит, объект спит и не стоит денег. Для владельца — [docs/CLOUD_KASSA_RU.md](../../docs/CLOUD_KASSA_RU.md).

Выкладка — шаг «Cloud cash desk» в `.github/workflows/deploy.yml` (только `main`, секреты
`CLOUDFLARE_WORKERS_API_TOKEN` и `CLOUDFLARE_ACCOUNT_ID`). Руками ничего не создаётся.

## Как запустить локально

```
npm ci
npm run build:web -w @bills/cloud-hub   # экраны TS в режиме облака → apps/cloud-hub/web-dist
npm run dev -w @bills/cloud-hub         # wrangler dev на http://127.0.0.1:8790, ADMIN_TOKEN=local-admin
node apps/cloud-hub/scripts/e2e.mjs new # новая кофейня, два устройства, заказ, WebSocket
```

После `build:web` перезапустите `wrangler dev`: список статики он читает при старте.

- `node scripts/make-trial-snapshot.ts <файл> [ключ] [дней] [заказов в день]` — копия пробной кофейни,
  как её шлёт браузер (`… 583104 8 100` — 6 МБ, 800 заказов; печатает и длинный ключ директора `MGR-…`).
- `node scripts/e2e.mjs import <файл> <ключ>` — переезд по шагу за вызов (время каждого шага), вход
  прежним ключом. `check <код> <ключ>` — после перезапуска; `load <код> <ключ> [n]` — цена заказа;
  `terms <код> <статус> [endsAt] [текст]`; `export <код> [файл]`; `steps` — время вызовов объекта.
- `node scripts/admin-check.mjs <файл> <ключ> [длинный ключ]` — весь договор admin API (Idempotency-Key,
  ключи пробной, условия, новый код директора, копия, защита). 19 проверок.
- `wrangler dev … --var COST_DEBUG:20` — ответы кофейни несут `x-ts-cost-top`: какие SQL читают больше.

## Admin API

Описание с формами ответов — в шапке `src/worker.ts` (`Authorization: Bearer <ADMIN_TOKEN>`, браузерам — 403):

| Вызов | Что делает |
|---|---|
| `POST /admin/cafes` `{venue, managerName, withMenu?, timezone?, terms?}` | новая кофейня → `{code, managerKey, …}` |
| `POST /admin/cafes/import` `{snapshot, newManagerKey?, managerName?, terms?}` | переезд пробной → `201 {code, status:'ready'}` или `202 {code, status:'importing'}` |
| `POST /admin/cafes/<code>/import/continue` | двигает переезд (или новую кофейню) дальше; те же ответы |
| `GET /admin/cafes/<code>` | состояние, условия, переезд, счётчики |
| `PUT /admin/cafes/<code>/terms` `{status, endsAt, message?}` | условия: `active` до `endsAt`, `permanent`, `ended` |
| `POST /admin/cafes/<code>/director-key` | новый код директора, прежние ключи и сессии директора закрыты |
| `GET /admin/cafes/<code>/export` | копия в формате пробной (`202` — «ещё готовлю», вызвать снова) |

`Idempotency-Key` на создании и переезде: повтор возвращает ту же кофейню (реестр `src/registry.ts`, 30 дней).
Переезд можно слать и файлом SQLite (`application/octet-stream`, поля — в заголовке `X-TS-Import`): без base64.
Клиент платформы — `apps/cloud/src/cloud-hub.ts` (сам вызывает `continue`, пока кофейня не `ready`).

## Как устроено

```
телефон / ПК ──https──▶ Worker (worker.ts) ──▶ Durable Object «кофейня K7F3…» (cafe-hub.ts)
  экраны TS             /c/<код>/api/*           HUB целиком: apps/hub/src
  (static assets,       /c/<код>/api/events ═WS═▶ SQLite объекта (shims/sqlite.ts)
   бесплатно)           /admin/*                 MiniFastify.inject → маршруты HUB
                                                 будильник: шаги переезда, копии, дедлайны HUB
```

| Часть | Файл | Что делает |
|---|---|---|
| Worker | `src/worker.ts`, `src/http.ts` | Маршрут `/c/<код>/…` к объекту кофейни (кривой код — 404 до объекта). Admin API: токен сравнивается за постоянное время, запросы браузеров (Origin, Sec-Fetch-*) — 403, `no-store`. CORS — только `ALLOWED_ORIGINS` (по умолчанию пусто: экраны с того же адреса). Лимиты тела: API 256 КБ, переезд 9 МБ (течёт в объект потоком). Логи Workers выключены: код кофейни — часть адреса. |
| Объект кофейни | `src/cafe-hub.ts` | HUB с включёнными для облака опциями (ниже). `/api/*` — `app.inject` в маршруты HUB. `/api/events` — WebSocket, ping отвечает рантайм. Один будильник: шаг переезда или копии, иначе ближайший дедлайн HUB (`hub.nextWakeAt()`), иначе нет будильника. Вход: троттлинг HUB считает «IP#устройство» (`X-TS-Device`), сверху — не больше 30 неверных ключей в час с одного IP. «Кто на смене?» выключен. |
| Опции HUB | `apps/hub/src/hub.ts`, `lean.ts`, `license.ts` | `timers: 'external'` — HUB не взводит таймеры, `tick()` на запросах и по будильнику, старт ничего не пишет. `leanReads` — `/api/state` не перечитывает историю. `outbox: false` — нет очереди событий для синхронизации, которой нет. `license.terms` — шлюз лицензии из условий TS, ключа подписи в облаке нет. На мини-ПК и в пробной всё выключено. |
| Условия | `src/terms.ts` | `active/permanent/ended` → статус лицензии HUB (те же «только чтение» и предупреждения, слова для кофейни). Новая кофейня — 14 дней. |
| Переезд и новая кофейня | `src/importer.ts`, `scripts/hub-schema.mjs` | Тело хранится частями как есть (без JSON-разбора мегабайт); шаги: base64 → байты, открыть в sql.js, описать таблицы (родители раньше детей), создать схему пачками, по 120 строк за шаг с прежними rowid, триггеры и счётчики. Каждый шаг — одна транзакция вместе со своим прогрессом: повтор шага безопасен. `outbox` и `idempotency_keys` не копируются. Новая кофейня — та же машина без копии: схема из сборки (миграции HUB, прогнанные в Node), потом `setupTrialClub`. |
| Копия | `src/exporter.ts` | «Скачать копию»: схема в пустую sql.js-базу пачками, строки по 120 (только те, что были на начало), файл, base64 частями в хранилище; ответ — поток JSON вокруг частей. Формат пробной (`ts-trial-backup`). |
| `node:sqlite` | `src/shims/sqlite.ts` | DatabaseSync/StatementSync поверх `ctx.storage.sql`, счёт строк (`x-ts-cost`). |
| Транзакции | `scripts/db-adapter.mjs` | Объект не принимает BEGIN/COMMIT/SAVEPOINT: сборка подменяет `transaction()` в `db.ts` на `transactionSync`, а `safely()` в `guard.ts` («Сторож») — на вложенную транзакцию хранилища. Изменится исходник — упадут сборка и тест. |
| Экраны | `apps/web/src/cloud/*`, `VITE_CLOUD_HUB=1` | «Код кофейни», строка кофейни до входа и «Сменить кофейню», значок «Облачная касса» (код, ссылка, срок, «Скачать копию» директору), id устройства в заголовке, страховочные опросы раз в 10 минут, при переподключении WebSocket экраны перечитывают всё, переподключение с паузой до 30 с, слова «Нет связи с облаком TS». Обычные сборки этого кода не загружают. |

## Что проверено (wrangler 4.151.3 / workerd 1.20261019, локально, 3 ноября 2026)

- **Новая кофейня** через admin API: 6 шагов схемы + 1 шаг настройки; вход ключом директора.
- **Переезд пробной 6,4 МБ** (800 заказов, 20 040 строк, из них 12 800 копируются): 135 шагов, ~2,4 с;
  записано 38 900 строк (с индексами). Миграция 022 догнала копию от 021. Вход прежним 6-значным ключом и
  длинным `MGR-…`. Повтор с тем же `Idempotency-Key` — та же кофейня.
- **Два устройства** в браузере (`127.0.0.1` и `localhost` — разные хранилища): директор на кассе, бариста по
  ссылке `#/cafe/<код>`. Заказ с кассы появился у бариста по WebSocket без опроса.
- **Условия**: `ended` с текстом TS — все экраны сразу «Только чтение» с этим текстом; `active` снова — работа.
- **Копия**: директор «Скачать копию» (12 шагов, 0,9 МБ), бариста — 403. Файл открыт в сборке пробной версии
  (`VITE_DEMO_LOCAL=1 VITE_TRIAL=1`): та же кофейня, заказы, вход прежним ключом, «только чтение» как в облаке.
- **Перезапуск** `wrangler dev`: кофейни, заказы, смена и сессии на месте; подъём объекта — 21 строка
  прочитана, 0 записано.
- **Защита**: admin без токена — 401, из браузера — 403, неизвестный код — 404, тело > 256 КБ — 413,
  `roster` пуст, чужой Origin не получает CORS.

### Сколько стоит одна операция (заголовок `x-ts-cost`, кофейня после переезда 800 заказов)

| Запрос | Строк прочитано | Строк записано | Было в прототипе |
|---|---|---|---|
| `GET /api/state` | **37, не растёт** (после сна +1 на оплату открытой смены, один раз) | 0 | 67 + ~15 на заказ (707 при 43) |
| `POST /api/counter/orders` | ~106 (свежая) … ~360 (100 заказов за день) | **45** | ~214 / ~71 |
| `POST /api/counter/orders/:id/stage` | 24 | 7 | 22 / 10 |
| `GET /api/counter/orders` | 15 + ~3 на заказ дня | 0 | так же |
| подъём объекта после сна | 21 | **0** | 22 / 0 |

Что изменилось: `/api/state` больше не считает весь outbox (раньше — каждое событие с открытия кофейни),
не перебирает все счета и все заказы бара (индексы по статусу), ожидаемая наличность смены — счётчик по
rowid. Заказ пишет на 26 строк меньше: нет outbox (строка + индекс + AUTOINCREMENT на событие).
Остаётся дневное: номер заказа и список «Выданные» читают заказы дня (`counter.ts`) — следующий кандидат.

### Процессор на шаг (Workers Free — 10 мс на запрос)

Измерено в Node (тот же V8 и SQLite, база в памяти) на кофейне 2,8 МБ / 4 940 строк (`test/move.test.ts`):

| Шаг | Среднее | Максимум |
|---|---|---|
| приём тела (`upload`, 3,7 МБ base64) | 7,8 мс | — |
| base64 → байты, 512 КБ | 2,0 | 4,3 |

| 120 строк | 3,3 | 10 (сборка мусора) |

Локально в `wrangler dev` время вызова объекта (вместе с записью на диск Windows): p50 12 мс, p90 26 мс,

## Лимиты Cloudflare (проверено 2 ноября 2026)

### Free (на весь аккаунт, сброс в 00:00 UTC)

| Лимит | Значение | Источник |
|---|---|---|
| Запросы к Workers | 100 000 в сутки, сверх — ошибка 1027 | [workers/platform/limits](https://developers.cloudflare.com/workers/platform/limits/) |
| CPU на запрос | 10 мс; «есть гибкость», если превышать редко | там же |
| Размер скрипта | 64 МиБ, без лимита на сжатый | там же |
| Тело запроса | 100 МБ (зависит от тарифа зоны) | там же |
| Запросы к Durable Objects | 100 000 в сутки | [durable-objects/platform/pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/) |
| Время работы DO | 13 000 ГБ·с в сутки | там же |
| SQLite: прочитано строк | 5 млн в сутки | там же |
| SQLite: записано строк | **100 000 в сутки**; каждое обновление индекса — отдельная строка | там же, [sqlite-storage-api](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/) |
| Хранение | 5 ГБ на аккаунт; на один объект 10 ГБ в таблице, но в FAQ сказано «1 ГБ на Free» (противоречие) | [pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/), [limits](https://developers.cloudflare.com/durable-objects/platform/limits/) |
| CPU у DO на Free | Прямо не указано: «те же лимиты, что у Workers». Закладываем 10 мс | [durable-objects/platform/limits](https://developers.cloudflare.com/durable-objects/platform/limits/) |

Как считается оплата:
- Время работы DO считается по 128 МБ. Счётчик останавливается, когда объект может уснуть
  (после 10 с без событий). Ожидающие `setTimeout`/`setInterval` уснуть не дают
  ([lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)).
- Открытие WebSocket — 1 запрос. Входящие сообщения считаются 20:1. Исходящие и ping бесплатны.
  Пока объект спит, ГБ·с не идут ([websockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)).
  Автоответ на ping не будит объект и не тарифицируется ([state API](https://developers.cloudflare.com/durable-objects/api/state/)).
- Вызов Worker → DO оплачивается и как запрос Worker, и как запрос DO.
- Будильник (alarm) — запрос DO плюс 1 записанная строка.
- Статика бесплатна и не ограничена ([static assets](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)).

### Сколько кофеен влезет

Модели (12 часов работы в день): **малая** — 150 заказов, 3 экрана; **средняя** — 400 заказов, 4 экрана.
Заказ — 4 команды; каждое событие заставляет каждый экран перечитать `/api/state` и свой список.

| Free, в сутки | Малая | Средняя |
|---|---|---|
| Запросы DO и Worker | ~4 700 → ~21 кофейня | ~14 700 → ~6 |
| Записано строк | ~13 000 (заказ 45 + этапы 3×7 + вход, смена) → **~7** | ~35 000 → **~2–3** |
| Прочитано строк | ~0,4 млн (`/api/state` плоский, списки — по дню) → ~12 | ~2,5 млн → ~2 |
| ГБ·с (объект спит между событиями) | ~850 → ~15 | ~2 300 → ~5 |
| **Итого на Free** | **~5–7 малых** | **~2 средних** |

Узкое место — записанные строки (100 000 в сутки на аккаунт). Переезд большой пробной (6 МБ) один раз
стоит ~39 000 записанных строк. На Paid ($5) — 50 млн строк в месяц: десятки кофеен, дальше ~$0,5–2 за
кофейню в месяц.

Хранение: ~5–15 КБ на заказ, малая кофейня — 0,3–0,8 ГБ в год. Бэкап: «Скачать копию» (директор) и
`GET /admin/cafes/<код>/export` (TS), плюс восстановление базы объекта на любой момент за 30 дней
(Point-in-Time Recovery SQLite-объектов, только на Cloudflare, руками через API).

## Где лежат данные

- Объект создаётся рядом с первым запросом и хранит данные там же
  ([data location](https://developers.cloudflare.com/durable-objects/reference/data-location/)).
- Юрисдикции есть только `eu`, `us`, `fedramp`. Хранилищ DO в Казахстане и Средней Азии нет:
  Алматы и Астана в списке мест, где DO не создаются
  ([where.durableobjects.live](https://where.durableobjects.live/region/eeur), неофициально).
- Запрос из Казахстана на практике приводит к созданию объекта во Франкфурте.
- Закон РК № 94-V «О персональных данных и их защите», ст. 12 п. 2: хранение персональных данных —
  «в базе … которые находятся на территории Республики Казахстан»
  ([adilet.zan.kz](https://adilet.zan.kz/rus/docs/Z1300000094)).
  - Ст. 16 разрешает трансграничную передачу, но не отменяет хранение в РК.
  - Штрафы — КоАП ст. 79, от 60 МРП (≈260 тыс. ₸, малый бизнес)
    ([КоАП](https://adilet.zan.kz/rus/docs/K1400000235)).
- В кофейне персональные данные — это имена сотрудников, IP и устройства входов, имена гостей на
  заказах, телефоны гостей в «Гостях» (лояльность).
- Значит, облачная касса на Cloudflare нарушает требование о хранении в РК так же, как Supabase.
  Об этом уже сказано в главном README. Нужен юрист.
- Варианты:
  - не хранить телефоны гостей в облаке;
  - держать основную копию в РК (VPS в Алматы с тем же HUB — это платно);
  - принять риск на пилот.


## Риски и что осталось

1. **Процессор на Free не проверен на Cloudflare.** Шаги переезда и копии — 1–5 мс в Node, но приём тела
   (6 МБ base64 — ~10–15 мс), открытие копии (~5 мс) и настройка новой кофейни (4–10 мс) близки к лимиту 10 мс.
   Cloudflare допускает редкие превышения; если приём упрётся в лимит (ошибка 1102), платформа повторит вызов
   с тем же `Idempotency-Key`, а лучше слать файл SQLite (`application/octet-stream`) — без base64. На Paid
   лимит 30 с.
2. **Записанные строки на Free** — главный предел (~5–7 малых кофеен); переезд 6 МБ — треть суточного лимита.
3. **Подъём объекта** (`buildApp` и сервисы HUB) — на каждом пробуждении; читает 21 строку, но процессор не
   измерен на Cloudflare.
4. **Дневные чтения** номера заказа и списка «Выданные» (`counter.ts`) растут с числом заказов за день.
5. **Код кофейни в адресе.** Логи Workers выключены в `wrangler.toml`; `wrangler tail` и чужие прокси увидят
   адрес. Код сам по себе не пускает в кассу.
6. **Ветвевая пауза HUB** («слишком много неверных ключей в филиале» — 50 в час) осталась: зная код, чужой
   может на 5 минут остановить вход по коротким ключам. Это цена защиты 6-значных ключей от перебора.
7. **ADMIN_TOKEN меняется при каждой выкладке**: несколько секунд между `wrangler secret put` и шагом секретов
   Supabase кабинет получает «не приняла ключ TS».
8. **Без интернета** устройство ничего не может («Нет связи с облаком TS»); команды уходят с Idempotency-Key,
   повтор безопасен. Очереди продаж офлайн нет — решение за владельцем.
9. **Данные вне РК** (Франкфурт) — см. выше; нужен юрист.
10. **Бильярд в облаке** не делался: ламп нет. Дедлайны предоплаченных игр, «Сторож» и брони уже будят объект
    будильником (`hub.nextWakeAt`).
11. **Фискализация** (Webkassa) — будущий `fetch` из объекта; повторы очереди — через тот же будильник.
