# План: TS в браузере и как приложение

Один и тот же интерфейс TS (`apps/web` — экраны клуба, `apps/cloud-web` — кабинет владельца) доходит до людей тремя путями. Идём по фазам: каждая следующая добавляет обёртку вокруг того же кода, а не пишет интерфейс заново.

| Фаза | Что | Для кого | Где берут |
|---|---|---|---|
| 1 | **PWA** — TS из браузера с иконкой на экране | планшеты официантов, экран зала, касса | адрес HUB клуба, кнопка «Установить» |
| 2 | **Приложение для ПК кассы и мини-ПК** (Tauri) | ПК кассира, экран зала на мини-ПК, сам HUB | установщик `.msi` / `.deb` |
| 3 | **Мобильное приложение владельца** (Capacitor) | владелец и управляющие | Google Play, App Store |

---

## Фаза 1. PWA: приложение из браузера

Цель: сотрудник открывает адрес HUB в браузере планшета или ПК кассира, нажимает «Установить» — и дальше работает с иконки, на весь экран, без адресной строки, с кэшем на случай обрыва Wi-Fi. Никаких магазинов приложений и установщиков: приложение раздаёт сам HUB клуба.

### Статус — ✅ этапы A, B, D, E и заголовки из C сделаны (ветка `claude/pwa-d4482d`)

Проверено в браузере на собранном `dist` через HUB (конфигурация `pwa-check`, `http://localhost:4800/`): манифест отдаётся как `application/manifest+json`, `navigator.serviceWorker.getRegistrations()` возвращает одну активную регистрацию со scope `/`, страница контролируется воркером с первой загрузки, консоль без ошибок, `/api/events` (SSE) и `/api/state` идут через воркер как обычные запросы. Баннер установки (по синтетическому `beforeinstallprompt`): [img/pwa-install-banner.jpg](img/pwa-install-banner.jpg), «Позже» запоминается. Обновление: правка `sw.js` → воркер в ожидании → баннер «Доступна новая версия» → «Обновить» → перезагрузка, вход сохранён. Инструкция для персонала — README, «Установка на планшет и ПК (PWA)».

Решения по ходу: `clientsClaim: true` при `skipWaiting: false` — первый воркер берёт под контроль страницу, которая его зарегистрировала (иначе следующая сборка активируется молча и баннеру нечего переключать), каждая следующая сборка ждёт нажатия; раз в час воркер сам спрашивает HUB о новой сборке. Иконки «TS» рисует `scripts/icons.mjs` чистым JS (буквы геометрией, PNG через `node:zlib`, без зависимостей и сети), результат закоммичен. По HTTP в сети клуба Chrome ставит приложение только после флага `chrome://flags/#unsafely-treat-insecure-origin-as-secure` на устройстве (описано в README), iPad — без ограничений. В Lighthouse 12+ нет категории «PWA»: установимость смотрят в DevTools → Application → Manifest; `npm run audit:pwa` гоняет Lighthouse через `npx @lhci/cli` без тяжёлых зависимостей в репозитории. Не сделано: HTTPS с локальным CA и имя `hub.local` (этап C, варианты 1–3), прогон на реальных планшетах и кассе — после развёртывания в клубе, PWA для `apps/cloud-web`.

### Как это выглядит для клуба

1. Управляющий открывает на планшете `http://hub.local` (или IP мини-ПК, например `http://192.168.1.10`).
2. Вводит ключ доступа → экран зала.
3. Браузер предлагает «Добавить на главный экран» / «Установить приложение». В Chrome на Android — баннер снизу, в Safari на iPad — «Поделиться → На экран „Домой“», в Chrome на Windows — иконка «Установить» в адресной строке.
4. На рабочем столе появляется иконка «TS». Запуск — сразу в полноэкранном режиме, экран не гаснет.
5. Пропал Wi-Fi: приложение открывается из кэша, показывает «Нет связи с HUB», кнопки возвращаются, как только связь вернётся. Данные никуда не теряются — они в HUB.
6. Обновили HUB: при следующем открытии приложение само подтягивает новую версию и показывает «Доступна новая версия — обновить».

### Что сделать в коде (`apps/web` + `apps/hub`)

#### Этап A. Манифест и иконки — ✅ готово
- `apps/web/public/manifest.webmanifest`: `name: "TS"`, `short_name: "TS"`, `start_url: "/#/"`, `display: "standalone"`, `orientation: "any"`, `theme_color`/`background_color` из токенов, `lang: "ru"`, `scope: "/"`.
- Иконки 192/512 px (maskable) + `apple-touch-icon` 180 px; сгенерировать из SVG-монограммы «TS» (та же, что в `BrandMark.tsx` и favicon; `scripts/icons.mjs`, без внешних сервисов).
- В `index.html`: `<link rel="manifest">`, `<meta name="apple-mobile-web-app-capable">`, `apple-mobile-web-app-status-bar-style`, `apple-mobile-web-app-title` = «TS», `theme-color` для обеих тем.
- Отдельные ярлыки в манифесте (`shortcuts`): «Зал», «Счета», «Сводка».

#### Этап B. Service worker — ✅ готово
- `vite-plugin-pwa` (Workbox) в `vite.config.ts`: стратегия `precache` для сборки (`index.html`, js, css, шрифт, иконки) и `NetworkOnly` для `/api/*` — данные всегда с HUB, никакого кэша команд.
- `registerType: "prompt"`: новая версия → баннер «Обновить» в оболочке (`Shell.tsx`), по нажатию `skipWaiting` + перезагрузка. Без принудительных обновлений посреди смены.
- Офлайн-страница не нужна: оболочка уже показывает «Нет связи с HUB» (`OfflineBanner`).
- Исключить из кэша `/api/events` (SSE) и `/api/dev/*`.

#### Этап C. Раздача с HUB — ✅ заголовки и тест, ⏳ HTTPS / hub.local
- HUB уже отдаёт `apps/web/dist` на `/` (`@fastify/static`, этап 1). Добавить правильные заголовки: `manifest.webmanifest` → `application/manifest+json`, `sw.js` → `Cache-Control: no-cache` (иначе обновления не доедут), `index.html` → `no-cache`.
- Service worker требует «безопасный контекст»: `http://<ip>` в локальной сети **не считается** безопасным в Chrome/Safari, исключение — только `localhost`. Решение для клуба — одно из:
  1. **HTTPS на HUB с локальным CA** (рекомендую): HUB при установке генерирует свой корневой сертификат (`deploy/linux/install.sh` → `bills ca init`), сертификат ставится на планшеты один раз (QR-код со страницы «Оборудование»), HUB слушает `https://hub.local:443`. Полный PWA, wake lock, камера для QR.
  2. **mDNS-имя `hub.local` + HTTP**: установка на главный экран работает в Android Chrome и iPad Safari как «ярлык», но без service worker (нет офлайн-кэша и баннера обновления). Самый простой старт для пилота.
  3. **Tailscale/внутренний домен с Let's Encrypt** — для сети клубов с облаком (этап 6): `club1.<домен-сети>` с настоящим сертификатом, DNS указывает на локальный IP.
- Для пилота: вариант 2 сразу, вариант 1 — в `deploy/` одной командой.

#### Этап D. Поведение «как приложение» — ✅ готово
- Полноэкранный режим и wake lock уже есть (`kiosk.ts`); в standalone-режиме прятать кнопку «На весь экран».
- Запрет масштабирования пальцами (`viewport maximum-scale=1`), `overscroll-behavior: none`, `user-select: none` на кнопках.
- Вход по ключу: опция «Запомнить устройство» — токен на 30 дней уже есть; добавить название устройства в список входов (есть на странице «Сотрудники»).
- Баннер «Установите TS» (событие `beforeinstallprompt`) с кнопкой — показывается один раз, пока не установлено; для iPad — подсказка с картинкой «Поделиться → На экран „Домой“».

#### Этап E. Проверка — ✅ в браузере, ⏳ на реальных устройствах
- Lighthouse PWA-аудит ≥ 90 в CI (`npm run audit:pwa` через `@lhci/cli` на собранном dist).
- Ручной прогон: Android Chrome (планшет), iPad Safari, Windows Chrome/Edge (касса): установка, запуск с иконки, обрыв Wi-Fi, обновление версии.
- Тест: HUB отдаёт манифест и `sw.js` с нужными заголовками (`node --test`).

То же самое (манифест + service worker) потом повторяется для `apps/cloud-web` — кабинет владельца тоже ставится с иконкой ещё до фазы 3.

### Чего PWA не умеет (и зачем фазы 2–3)
- **Тихая печать чека** без системного диалога — браузер всегда показывает диалог печати (`window.print`). Для кассы это лишний клик на каждом чеке → фаза 2.
- **Настоящий киоск**: PWA можно свернуть, закрыть, открыть рядом браузер; автозапуск при включении ПК — только ярлыком в автозагрузке → фаза 2.
- **Push-уведомления на iPhone** работают только у PWA, добавленной на экран «Домой», и ненадёжно; владельцу нужны тревоги, которые точно дойдут → фаза 3.

## Фаза 2. Приложение для ПК кассы и мини-ПК

**TS для Windows и Linux на [Tauri](https://tauri.app)**: тот же веб-интерфейс `apps/web` в нативном окне. Окно использует системный движок (WebView2 на Windows, WebKitGTK на Linux), поэтому установщик весит **≈ 10 МБ**, а не 100+ МБ, как у Electron.

### Что получает клуб
- **Ярлык «TS» и автозапуск**: ПК кассы включили — TS открылся сам, сразу на экране входа.
- **Киоск-режим**: окно на весь экран без рамки, нельзя свернуть или закрыть без ключа управляющего; экран не гаснет. Для экрана зала на мини-ПК у телевизора — «только зал», без меню.
- **Тихая печать чека**: «Оплатить» → чек сразу выходит на термопринтер 58/80 мм, без диалога. Принтер выбирается один раз в настройках устройства. Та же вёрстка чека (`cash/print/*`), печатается через системный принтер; позже — прямой ESC/POS по USB/сети (быстрее, с отрезкой бумаги и открытием денежного ящика).
- **Подключение к HUB без адресов**: приложение само находит HUB в сети (mDNS `hub.local`) или спрашивает адрес один раз. Защищённый контекст не нужен — проблема HTTPS из фазы 1 (этап C) для ПК исчезает.
- **По желанию — HUB внутри**: на мини-ПК клуба один установщик ставит и HUB как службу (Windows-служба / systemd), и окно экрана. Для маленького клуба «один ПК = HUB + касса» без командной строки. Сейчас это делают `deploy/linux/install.sh` и `deploy/windows/install.ps1`; установщик вызывает их же.
- **Автообновление**: приложение проверяет новую версию на HUB клуба (HUB раздаёт файл обновления, как сейчас раздаёт `apps/web/dist`) или в GitHub Releases; обновление подписано ключом, ставится между сменами по кнопке «Обновить», без потери открытых игр (данные в HUB).

### Статус — ✅ шаги 2.1–2.6 сделаны (ветка `claude/desktop-fbb23d`), ⏳ 2.7 — проверка на реальном ПК кассы
`apps/desktop` (Tauri 2): окно открывает HUB, первый запуск ищет HUB (`hub.local`, этот ПК, сеть /24), киоск с выходом по ключу управляющего, автозапуск, тихая печать `print_receipt` (WebView2 / WebKitGTK) с выбором принтера, установка HUB скриптами `deploy/`, `.msi`/`.deb` в GitHub Actions, автообновление из GitHub Releases с подписью. Подробности — README, раздел «Приложение для ПК». Не сделано: режим «экран зала» без меню (окно открывает обычный интерфейс; для мини-ПК у телевизора — вход сотрудником с правом только на зал), раздача обновлений с HUB клуба (только GitHub Releases), прямой ESC/POS.

## Фаза 3. Мобильное приложение владельца

**TS для владельца на Android и iPhone на [Capacitor](https://capacitorjs.com)**: обёртка над кабинетом владельца `apps/cloud-web`. Интерфейс тот же, что в браузере; приложение добавляет то, чего браузер на телефоне не даёт надёжно.

### Статус — ✅ шаги 3.1–3.3 сделаны, 3.4 — чек-лист (ветка `claude/mobile-1a2fcb`)

- `apps/mobile` (Capacitor 8, appId `kz.ts.owner`): кабинет встроен в сборку, адрес облака — в приложении (экран входа или QR), иконка и заставка «TS». Debug APK собирается `npm run build:android-debug -w @bills/mobile`; iOS-проект настроен, собирается только на Mac. Подробно — [apps/mobile/README.md](../apps/mobile/README.md).
- Push: облако (`apps/cloud/src/push.ts`) — устройства, правила «какие тревоги кому», очередь с защитой от повторов, FCM HTTP v1 по ключу сервисного аккаунта; без ключа — режим «push выключены» с логом. Кроме тревог HUB облако само сообщает «HUB пропал со связи» и «смена не закрыта». Тесты — на фейковом FCM.
- Вход по ключу `OWNER-…` и QR: ключ создаётся в кабинете (страница «Телефон и уведомления»), телефон сканирует QR с адресом облака и ключом. Ключи HUB клуба для входа в облако не подходят — это разные системы ключей.
- Отличие от плана: интерфейс **встроен** в приложение (а не грузится с облака) — запуск без сети и требование Apple 4.2; поэтому любая правка интерфейса — новая версия в магазинах.
- Не сделано: биометрия и Keystore/Keychain (токен сейчас в Preferences приложения), показ push при открытом приложении, вёрстка остальных страниц кабинета под ширину телефона, проверка на реальном устройстве с Firebase. Публикация — [MOBILE_RELEASE_RU.md](MOBILE_RELEASE_RU.md).

### Что получает владелец
- **Push-уведомления о тревогах**, даже когда приложение закрыто: свет горит без игры (`LIGHT_WITHOUT_GAME`), игра идёт без света (`LAMP_DARK_DURING_GAME`), пропало электричество и клуб на ИБП (`POWER_ON_BATTERY`, `POWER_CRITICAL`), HUB клуба пропал со связи, крупный возврат или отмена игры. Нажал на уведомление — открылся нужный клуб и тревога.
- **Вход по QR**: на экране TS в клубе (или в кабинете на ПК) владелец показывает QR со своим ключом — телефон сканирует и входит, без ручного набора `OWNER-…`. Сессия хранится в защищённом хранилище телефона; вход по отпечатку/Face ID.
- Выручка, загрузка, смены и тарифы всех клубов — как в кабинете, плюс виджет «сегодня» на экране телефона (позже).

### Что сделать

## Сравнение подходов

| | PWA | Tauri | Electron | Capacitor | Нативное (Kotlin/Swift) |
|---|---|---|---|---|---|
| Платформы | любые с браузером | Windows, Linux, macOS | Windows, Linux, macOS | Android, iOS | одна платформа на код |
| Размер | 0 (из браузера) | ≈ 10 МБ | ≈ 100–150 МБ | ≈ 5–15 МБ | ≈ 5–20 МБ |
| Интерфейс TS как есть | да | да | да | да | нет, писать заново |
| Тихая печать, киоск, автозапуск | нет | да | да | — | да |
| HUB как служба в установщике | нет | да | да | — | — |
| Push на телефон | ограниченно (iPhone — плохо) | — | — | да | да |
| Магазины | не нужны | не нужны | не нужны | нужны | нужны |
| Стоимость поддержки | минимальная | низкая | средняя (тяжёлый, частые обновления Chromium) | низкая | высокая (два отдельных приложения) |
| Наш выбор | **фаза 1** | **фаза 2** | запасной вариант, если WebView2/WebKitGTK подведёт на старом ПК кассы | **фаза 3** | не нужно |

## Рекомендуемый порядок

1. **Фаза 1 (PWA)** — сразу, вместе с пилотом: дёшево, работает на всех планшетах, ничего не надо ставить.
2. **Фаза 2 (Tauri)** — когда в пилоте появится касса с термопринтером: тихая печать и киоск окупаются на первой же неделе смен.
3. **Фаза 3 (Capacitor)** — когда облако (этап 6) работает в проде и у владельца больше одного клуба: push о тревогах — главная причина ставить приложение.

## Что остаётся тем же кодом

- **Весь интерфейс**: `apps/web` (экраны клуба) и `apps/cloud-web` (кабинет владельца) — одни и те же во всех трёх фазах. Отличия — только в нескольких местах через проверку «где запущены» (`window.__TAURI__`, `Capacitor.isNativePlatform()`): печать, поиск HUB, push, сканер QR.
- **HUB и облако**: `apps/hub`, `apps/cloud`, `packages/domain` не меняются; добавляются только раздача файлов обновления (фаза 2) и рассылка push (фаза 3).
- **Права, вход по ключу, данные**: те же токены, тот же `permissions.ts`; приложение не хранит деньги и игры у себя — всё в HUB.
- **Установка HUB**: те же скрипты `deploy/linux` и `deploy/windows`; установщик фазы 2 их только вызывает.
- **Тесты**: `npm test` проверяет HUB и облако как сейчас; обёртки проверяются ручным прогоном на устройствах.

## Что НЕ входит
- Отдельные нативные приложения на Kotlin/Swift — не нужны, пока Capacitor справляется.
- Приложение сотрудников в магазинах — сотрудникам хватает PWA и приложения для ПК.
- macOS-сборка Tauri — возможна тем же кодом, но не нужна клубам; по запросу.
