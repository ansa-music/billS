# Публикация мобильного приложения владельца TS

Чек-лист для того, кто выпускает приложение **TS** для владельца в Google Play и App Store. Что это за приложение и зачем оно нужно — в [docs/APP_PLAN_RU.md](APP_PLAN_RU.md), раздел «Фаза 3». Где размещается облако и почему в РК — в [apps/cloud/README.md](../apps/cloud/README.md).

Коротко о том, что публикуем:

| | |
|---|---|
| Проект | `apps/mobile` — Capacitor 8; внутри собранный кабинет владельца `apps/cloud-web` |
| Идентификатор | `kz.ts.owner` (одинаковый в Android и iOS), имя на экране — **TS** |
| Android | minSdk 26 (Android 8.0; столько требует QR-сканер), targetSdk/compileSdk 36 |
| Push | Firebase Cloud Messaging, плагин `@capacitor-firebase/messaging`; на iPhone — через APNs |
| QR-сканер | `@capacitor/barcode-scanner` (нужна камера) |
| Вход | почта + пароль или ключ `OWNER-…`; QR с ключом создаётся в кабинете на странице «Телефон и уведомления» |
| Какие данные уходят в облако | почта и имя владельца, токен устройства FCM, модель телефона |

> Секреты (keystore, пароли к нему, `.p8`, ключ сервисного аккаунта) **никогда не кладём в git** и не пересылаем в мессенджерах. Хранилище — менеджер паролей компании + резервная копия на отдельном носителе.

## 1. Один раз: аккаунты, Firebase, ключи

### 1.1. Аккаунты разработчика
- [ ] Решить, на кого регистрируем: **организация** (ТОО/ИП) или физлицо. Рекомендуем организацию: в магазине будет имя компании, а в Google Play не нужно закрытое тестирование 12 тестировщиков × 14 дней (раздел 6).
- [ ] Для организации получить бесплатный **D-U-N-S** номер: <https://developer.apple.com/enroll/duns-lookup/> (поиск и заявка, 1–14 дней). Он нужен и Apple, и Google для аккаунта организации. Название и адрес в D-U-N-S должны совпадать с регистрационными документами.
- [ ] **Google Play Console** — <https://play.google.com/console/signup>, **$25 один раз**. Проверка личности/организации — от нескольких дней. Указать публичную почту и телефон разработчика.
- [ ] **Apple Developer Program** — <https://developer.apple.com/programs/enroll/>, **$99 в год**. Для организации — через Apple ID на корпоративной почте, нужен D-U-N-S и право подписи от компании. Поставить напоминание о продлении: при просрочке приложение пропадает из App Store.
- [ ] В **App Store Connect** (<https://appstoreconnect.apple.com>) подписать соглашения в «Business» (даже для бесплатного приложения нужен Free Apps Agreement).
- [ ] Завести общую почту поддержки (например `support@…`) — она пойдёт в карточки магазинов и в политику конфиденциальности.

### 1.2. Проект Firebase
- [ ] Создать проект в <https://console.firebase.google.com> (имя, например, `ts-owner`). **Google Analytics не включать** — он нам не нужен и добавит пункты в Data safety / App Privacy.
- [ ] Добавить **Android-приложение** с package name `kz.ts.owner`. Скачать `google-services.json` → положить в `apps/mobile/android/app/google-services.json`.
- [ ] Добавить **iOS-приложение** с bundle ID `kz.ts.owner`. Скачать `GoogleService-Info.plist` → положить в `apps/mobile/ios/App/App/` и добавить в target **App** в Xcode (иначе файл не попадёт в сборку).
- [ ] Решить, коммитим ли эти два файла. Секретов в них нет (это публичные идентификаторы проекта), но если в git их не держим — описать в README, откуда их брать перед сборкой.
- [ ] В Google Cloud Console проекта убедиться, что включён **Firebase Cloud Messaging API** (это v1): <https://console.cloud.google.com/apis/library/fcm.googleapis.com>. Старый Legacy API не используем — облако отправляет только через HTTP v1.

### 1.3. APNs-ключ (push на iPhone)
- [ ] <https://developer.apple.com/account/resources/authkeys/list> → **+** → отметить **Apple Push Notifications service (APNs)** → скачать `AuthKey_XXXXXXXXXX.p8`. Скачать можно **только один раз** — сразу в менеджер паролей.
- [ ] Записать **Key ID** (10 символов) и **Team ID** (Membership → Team ID).
- [ ] Firebase Console → Project settings → **Cloud Messaging** → Apple app configuration → APNs Authentication Key → загрузить `.p8`, указать Key ID и Team ID. Один ключ работает и для отладки, и для продакшена.
- [ ] В <https://developer.apple.com/account/resources/identifiers/list> у App ID `kz.ts.owner` включить capability **Push Notifications** (Xcode обычно делает это сам при включении capability, но проверить).

### 1.4. Сервисный аккаунт для облака
- [ ] Google Cloud Console → IAM & Admin → **Service Accounts** (<https://console.cloud.google.com/iam-admin/serviceaccounts>) → создать `ts-cloud-push`.
- [ ] Выдать **одну** роль: **Firebase Cloud Messaging API Admin** (`roles/firebasecloudmessaging.admin`). Не выдавать Owner/Editor и «Firebase Admin» — облаку нужна только отправка сообщений.
- [ ] Keys → Add key → JSON → скачать. Это секрет: кто им владеет, может слать push всем владельцам.
- [ ] Положить на сервер облака (в РК) с правами только для пользователя службы (`chmod 600`) и указать путь в `CLOUD_FCM_SERVICE_ACCOUNT=/etc/ts-cloud/fcm.json`. Альтернатива для контейнеров — содержимое целиком в `CLOUD_FCM_SERVICE_ACCOUNT_JSON`.
- [ ] Перезапустить облако и проверить лог: должна быть строка `Push включены: FCM, проект <id>`. Строка `Push выключены: нет ключа FCM` — значит, переменная не прочиталась; облако при этом работает, но уведомления не уходят.
- [ ] Записать в календарь ревизию ключа раз в год; старый ключ удалять в той же консоли после замены.

## 2. Android: подпись и сборка релиза

### 2.1. Upload keystore (один раз)
- [ ] Создать ключ загрузки (JDK 21, `keytool` идёт с Android Studio):
  ```sh
  keytool -genkeypair -v -keystore ts-upload.jks -alias ts-upload \
    -keyalg RSA -keysize 2048 -validity 10000 \
    -dname "CN=TS, O=<Компания>, C=KZ"
  ```
- [ ] Файл `ts-upload.jks` хранить **вне репозитория** (например `~/.ts-keys/ts-upload.jks`) + копия в менеджере паролей вместе с паролями хранилища и ключа.
- [ ] Создать `apps/mobile/android/keystore.properties` (в `.gitignore`, проверить `git check-ignore`):
  ```properties
  storeFile=/home/<user>/.ts-keys/ts-upload.jks
  storePassword=...
  keyAlias=ts-upload
  keyPassword=...
  ```
- [ ] Убедиться, что `apps/mobile/android/app/build.gradle` читает `keystore.properties` в `signingConfigs.release` и что без файла релиз не собирается молча неподписанным.
- [ ] При первой загрузке в Play Console включить **Play App Signing** (по умолчанию для новых приложений): Google хранит ключ подписи приложения, а наш `ts-upload.jks` — только ключ загрузки. Потеряли upload-ключ — его можно сбросить через поддержку Play, приложение при этом не теряется.
- [ ] Сохранить SHA-1/SHA-256 **ключа подписи приложения** из Play Console → Setup → App signing (пригодятся, если позже понадобятся Google-сервисы, проверяющие подпись).

### 2.2. Сборка `.aab` (каждый релиз)
- [ ] Поднять версию в `apps/mobile/android/app/build.gradle`:
  - `versionCode` — целое число, **+1 каждую загрузку** в Play (даже в тестовый трек; повтор не примут);
  - `versionName` — то, что видит пользователь, например `1.2.0`. Держим одинаковым с версией iOS.
- [ ] Собрать: `npm run build:android-release` из `apps/mobile`. Это то же самое, что:
  ```sh
  cd apps/mobile
  npm run build                 # собирает кабинет в www
  npx cap sync android          # копирует www и плагины в android/
  cd android && ./gradlew bundleRelease
  ```
- [ ] Результат: `apps/mobile/android/app/build/outputs/bundle/release/app-release.aab`. Его и загружаем в Play Console (APK магазин для новых приложений не принимает).
- [ ] Проверить подпись: `jarsigner -verify -verbose app-release.aab` → «jar verified», в сертификате `CN=TS`.

## 3. iOS: сборка и TestFlight

Нужен **Mac** с актуальным Xcode. С апреля 2026 App Store принимает сборки только с iOS 26 SDK, то есть **Xcode 26+** (Xcode 16 уже не подходит). Нет Mac — облачная сборка: [Codemagic](https://codemagic.io), [Ionic Appflow](https://ionic.io/appflow) или GitHub Actions на `macos-*` раннере (подпись через App Store Connect API key).

- [ ] Платформа уже добавлена (`npx cap add ios` сделан); каждый релиз начинаем с:
  ```sh
  cd apps/mobile && npm run build && npx cap sync ios
  cd ios/App && pod install     # если проект на CocoaPods; на SPM шаг не нужен
  open App.xcworkspace          # (или App.xcodeproj для SPM)
  ```
- [ ] Target **App** → General: Bundle Identifier `kz.ts.owner`, Display Name `TS`, **Version** = `versionName` Android, **Build** — +1 каждую загрузку.
- [ ] Решить про iPad: если в Deployment Info оставлен iPad, Apple потребует скриншоты iPad 13″ и проверит интерфейс на планшете. Проще оставить **только iPhone**.
- [ ] **Signing & Capabilities**: Team — наша организация, «Automatically manage signing».
  - [ ] **+ Capability → Push Notifications**.
  - [ ] **+ Capability → Background Modes** → отметить **Remote notifications**.
- [ ] `ios/App/App/Info.plist`:
  - [ ] `NSCameraUsageDescription` = «Камера нужна, чтобы отсканировать QR-код входа из кабинета TS.» Без этой строки приложение падает при открытии сканера и отклоняется проверкой.
  - [ ] `ITSAppUsesNonExemptEncryption` = `NO` (используем только стандартный HTTPS) — тогда не будет вопроса об экспортном контроле при каждой загрузке.
- [ ] Проверить, что `GoogleService-Info.plist` в target App и что `AppDelegate` настроен по инструкции `@capacitor-firebase/messaging` (Firebase инициализирован, APNs-токен передаётся в Firebase).
- [ ] Схема **Release**, устройство «Any iOS Device (arm64)» → **Product → Archive** → Organizer → **Distribute App → App Store Connect → Upload**.
- [ ] В App Store Connect → TestFlight дождаться обработки сборки (10–30 мин), заполнить «What to Test», добавить внутренних тестировщиков (до 100 человек из команды, без проверки Apple). Внешние тестировщики — после короткой бета-проверки.
- [ ] Поставить сборку из TestFlight на реальный iPhone и пройти раздел 5. **Push на симуляторе не проверяем** — только на устройстве.

### 4.4. Политика конфиденциальности
- [ ] Опубликовать на нашем сайте по постоянному **HTTPS-адресу** (одинаковый URL в обоих магазинах и в приложении — ссылка на экране входа/настроек). Языки: русский и казахский, по возможности английский для проверяющих.
- [ ] Что в ней должно быть:
  - кто оператор данных (юрлицо, БИН, адрес, почта для обращений);
  - какие данные собираем: почта и имя владельца, хеш пароля / ключ входа, токен устройства FCM, модель телефона, данные клубов (выручка, смены, тревоги), которые владелец и так ведёт в TS;
  - зачем: вход, показ данных клубов, отправка push о тревогах;
  - где хранятся: на серверах в Республике Казахстан (закон РК «О персональных данных и их защите»);
  - кому передаются: Google (Firebase Cloud Messaging) и Apple (APNs) — только токен устройства и текст уведомления, для доставки push; больше никому, не продаём, рекламы и аналитики нет;
  - сколько храним: пока действует учётная запись; токен устройства удаляется при выходе из приложения;
  - права пользователя: доступ, исправление, удаление, отзыв согласия; как удалить учётную запись (раздел 6.3);
  - защита: HTTPS, доступ по ролям;
  - дети: приложение не предназначено для лиц младше 18 лет;
  - дата редакции и как сообщаем об изменениях.

### 4.5. Data safety (Google) — ответы
- [ ] «Собирает или передаёт ли приложение данные?» — **Да**.
- [ ] «Все данные шифруются при передаче?» — **Да** (только HTTPS).
- [ ] «Можно запросить удаление данных?» — **Да**, + URL страницы удаления (Google требует его для приложений с учётными записями).
- [ ] Типы данных (все — **собираются**, **не передаются третьим лицам** в смысле Google: доставка push через FCM считается обработкой поставщиком услуг; **обязательны**; цель — **App functionality** и **Account management**):
  - Personal info → **Name**, **Email address**;
  - Device or other IDs → **токен FCM** (модель телефона указываем здесь же — для осторожности);
  - Financial info → **не выбираем**: выручка клубов — данные бизнеса, а не платёжные данные пользователя. Если проверка спросит — пояснить так же.
- [ ] Location, Contacts, Photos, Analytics, Advertising ID — **не собираем**. Проверить объединённый манифест (`android/app/build/intermediates/merged_manifests/…`), что нет `com.google.android.gms.permission.AD_ID`; в Play Console → App content → Advertising ID ответить «Нет».

### 4.6. App Privacy (Apple) — ответы
- [ ] Data Types: **Contact Info → Name, Email Address**; **Identifiers → Device ID** (токен push). Модель устройства Apple отдельно не спрашивает — не указываем как отдельный тип.
- [ ] Для каждого: Purpose — **App Functionality**; Linked to the user — **Yes**; Used for tracking — **No**.
- [ ] Tracking (ATT) — **не используем**, `NSUserTrackingUsageDescription` не добавляем.
- [ ] Privacy Policy URL — из 4.4.

### 4.7. Возрастной рейтинг
- [ ] Google: анкета IARC — категория «Утилиты/производительность», на все вопросы о насилии, азартных играх, алкоголе, общении пользователей — **Нет** → ожидаемо «3+ / Для всех».
- [ ] Apple: анкета Age Rating — всё **None/No** → **4+**. Азартных игр нет: бильярд в приложении — это учёт времени столов, а не игра на деньги.
- [ ] Google: Target audience — **18+** (бизнес-приложение), «Привлекает ли детей» — Нет.

### 4.8. Тестовый вход для проверяющих
- [ ] Облако, к которому ходит релизная сборка, **доступно из интернета по HTTPS** (проверяющие Apple в США, Google — из разных стран; не закрывать файрволом по стране).
- [ ] Завести **демо-владельца** на стенде/в проде: отдельная почта (например `review@…`), пароль, 1–2 демо-клуба с правдоподобной выручкой, сменами и хотя бы одной тревогой. Никаких реальных клиентских данных.
- [ ] Дополнительно — постоянный ключ `OWNER-…` этого демо-владельца (на случай, если проверяющий захочет войти по ключу). QR проверяющий отсканировать не сможет — в пояснении это написать.
- [ ] Google: App content → **App access** → «Весь функционал или его часть ограничен» → логин, пароль, инструкция.
- [ ] Apple: App Review Information → Sign-in required → логин/пароль; в **Notes**:
  > TS is a B2B app for owners of billiard clubs that already use the TS system. Accounts are created by our administrator when a club is connected; there is no sign-up in the app. Demo account: see above. To trigger a demo alert push, … (описать, как вызвать тестовую тревогу или приложить видео). QR login: the QR code is shown in the TS web cabinet; you can use the key below instead.
- [ ] Не менять пароль демо-владельца и не удалять демо-клубы, пока идёт проверка (и вообще — при каждом обновлении проверяют заново).

### 4.9. Разрешения и обоснование
| Разрешение | Платформа | Зачем | Когда спрашиваем |
|---|---|---|---|
| `POST_NOTIFICATIONS` | Android 13+ | push о тревогах в клубах | после входа, с пояснением на экране |
| Уведомления (UNUserNotificationCenter) | iOS | то же | после входа |
| `CAMERA` | Android | сканировать QR входа | только при нажатии «Войти по QR» |
| `NSCameraUsageDescription` | iOS | то же | то же |
| `INTERNET` | Android | связь с облаком | системное, не спрашивается |

- [ ] Других разрешений в объединённом манифесте нет (проверить после `bundleRelease`); лишнее — удалить через `tools:node="remove"`.
- [ ] Отказ в разрешении не ломает приложение: без уведомлений кабинет работает, без камеры остаётся вход по почте и ключу.

## 5. Перед каждой отправкой в магазин

Прогон на **реальных** устройствах: один Android (лучше 13+ и один старый, 7–9) и один iPhone, сборка из релизного `.aab` (через внутреннее тестирование Play) и из TestFlight.

- [ ] Версия увеличена: Android `versionCode` +1, iOS Build +1, `versionName`/Version совпадают и отличаются от прошлого релиза.
- [ ] Адрес облака в сборке — **HTTPS** продакшена (не `localhost`, не IP стенда).
- [ ] В release нет cleartext: `android:usesCleartextTraffic` не `true`, в `capacitor.config` нет `server.url` и `cleartext: true`; на iOS нет `NSAllowsArbitraryLoads`.
- [ ] Вход по почте и паролю работает; неверный пароль — понятная ошибка.
- [ ] Вход по QR: в кабинете на ПК «Телефон и уведомления» → QR → скан телефоном → вход без ввода ключа. Отказ в доступе к камере → понятное сообщение.
- [ ] Вход по ключу `OWNER-…` вручную.
- [ ] Push доходит: устройство появилось в кабинете в списке телефонов (с моделью); тестовая тревога в демо-клубе → уведомление пришло при **закрытом** приложении, при свёрнутом и при открытом.
- [ ] Тап по уведомлению открывает **нужный клуб** и тревогу (проверить из закрытого состояния — холодный старт).
- [ ] Настройка «какие тревоги присылать» действует: выключенный тип не приходит.
- [ ] **Выход** удаляет устройство: телефон пропал из списка в кабинете, push на него больше не приходят.
- [ ] Без сети: при запуске виден **офлайн-баннер**, приложение не белый экран; сеть вернулась — данные обновились.
- [ ] Повторный запуск после перезагрузки телефона: сессия сохранилась, вход не нужен.
- [ ] Иконка, имя «TS» и заставка правильные; нет отладочных надписей и тестовых данных.
- [ ] В облаке в логе нет ошибок отправки FCM (`UNREGISTERED`, `SENDER_ID_MISMATCH`, `THIRD_PARTY_AUTH_ERROR` — последняя значит, что APNs-ключ не загружен в Firebase).
- [ ] Обновлены тексты «Что нового» и, если менялся интерфейс, скриншоты.

## 6. Проверка в магазинах

### 6.1. Google Play
- [ ] Порядок: Internal testing (сразу, без проверки) → Closed testing → Production.
- [ ] **Новый личный аккаунт** (создан после ноября 2023): перед первым выпуском в Production обязателен **закрытый тест не менее чем с 12 тестировщиками, которые 14 дней подряд остаются в тесте**, затем заявка на доступ к Production. Для **аккаунта организации** это требование **не действует**.
- [ ] Сроки: первая проверка нового аккаунта — **до 7 дней**, дальше обычно от нескольких часов до 1–3 дней. Закладываем неделю на первый выпуск.
- [ ] Перед отправкой Play Console → **Publishing overview**: все пункты App content (политика, App access, Ads, Data safety, рейтинг, Target audience, Government apps — «Нет», Financial features — «Нет») зелёные.
- [ ] Выпуск в Production — сначала **staged rollout** 20 % → через 1–2 дня 100 %, если в Android vitals нет сбоев.

### 6.2. App Store
- [ ] Сроки: обычно **1–2 дня**; при замечании — ответ в Resolution Center и повтор, ещё 1–2 дня.
- [ ] Частые причины отказа и как отвечаем:
  - **4.2 Minimum Functionality** («это просто сайт в обёртке»). Ответ: приложение даёт то, чего нет в браузере — **push-уведомления о тревогах** при закрытом приложении с переходом к клубу, **вход по QR через камеру**, хранение сессии на устройстве, работа интерфейса без загрузки с сервера (встроен в сборку, офлайн-баннер). В Notes приложить короткое видео с push и QR.
  - **5.1.1 Data Collection / вход обязателен**. Ответ: это B2B-приложение для существующих клиентов; учётную запись владельца создаёт администратор TS при подключении клуба, регистрации в приложении нет; для проверки выдан демо-доступ (4.8). Не требовать в приложении лишних данных, кроме входа.
  - **5.1.1(v) Удаление учётной записи**. Строго обязательно, если учётную запись можно создать в приложении; у нас нельзя, но проверяющие всё равно часто спрашивают. Решение: в приложении в настройках пункт **«Удалить учётную запись»**, который открывает запрос на удаление (форма на сайте / письмо в поддержку с указанием почты) и объясняет срок исполнения; то же — страница в кабинете. Этот же URL указываем в Google Data safety.
  - **2.1 App Completeness** — демо-вход не работает или облако недоступно. Перед отправкой самим войти под демо-владельцем с мобильного интернета.
  - **5.1.1 / Info.plist** — нет или слишком общий текст `NSCameraUsageDescription`.
  - **2.3 Metadata** — скриншоты не из приложения или с макетами устройства, не совпадающими с реальным экраном.
- [ ] После одобрения выбрать «Manually release» или «Automatically release»; для первого выпуска — вручную, после финального прогона раздела 5 на сборке из TestFlight.

## 7. Обновления

- [ ] **Без магазина менять нельзя ничего в интерфейсе.** В нашей реализации кабинет `apps/cloud-web` **встроен в сборку** приложения (папка `www` внутри `.aab`/`.ipa`), а не грузится с облака. Любая правка интерфейса кабинета, которую должны увидеть пользователи приложения, = **новая версия** в обоих магазинах (раздел 2.2, 3, 5).
- [ ] Без магазина меняется только то, что живёт на сервере: данные, правила тревог, тексты push, которые формирует облако, API облака (при условии обратной совместимости — старые версии приложения у владельцев остаются месяцами).
- [ ] Это **отличается** от предположения в [APP_PLAN_RU.md](APP_PLAN_RU.md) («мелкие правки интерфейса можно доставлять без магазина, интерфейс грузится с облака»). Почему выбрали встроенный интерфейс:
  - **офлайн-запуск**: приложение открывается и показывает офлайн-баннер без сети, а не пустой экран;
  - **проверка Apple 4.2**: приложение, которое просто открывает удалённый сайт, отклоняют чаще; встроенный интерфейс + нативные push и QR — надёжный аргумент;
  - предсказуемость: версия интерфейса всегда совпадает с версией нативных плагинов, а проверенная магазином сборка — с тем, что реально у пользователя.
- [ ] Следствие для облака: API должно поддерживать **как минимум предыдущую версию** приложения. Ломающие изменения — только с проверкой версии приложения и экраном «Обновите приложение».
- [ ] Ритм: копить правки интерфейса и выпускать раз в 2–4 недели; срочные исправления — отдельным релизом (Apple позволяет запросить ускоренную проверку: <https://developer.apple.com/contact/app-store/?topic=expedite>).
- [ ] Каждое обновление проходит раздел 5 целиком и повышает `versionCode` / Build.
- [ ] Раз в год: targetSdk Android под новое требование Google (обычно к августу), Xcode/iOS SDK под требование Apple (обычно к апрелю), продление Apple Developer Program, ревизия ключа сервисного аккаунта.
