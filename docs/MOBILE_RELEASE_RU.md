# Публикация мобильного приложения владельца TS

Как выпустить приложение **TS** для владельца: быстрый путь — готовый APK на GitHub (раздел 0, хватает для начала), полный — Google Play и App Store (разделы 1–7). Что это за приложение и зачем оно нужно — в [docs/APP_PLAN_RU.md](APP_PLAN_RU.md), раздел «Фаза 3». Где размещается облако и почему в РК — в [apps/cloud/README.md](../apps/cloud/README.md).

Коротко о том, что публикуем:

| | |
|---|---|
| Проект | `apps/mobile` — Capacitor 8; внутри собранный кабинет владельца `apps/cloud-web` |
| Идентификатор | `kz.ts.owner` (одинаковый в Android и iOS), имя на экране — **TS** |
| Android | minSdk 26 (Android 8.0; столько требует QR-сканер), targetSdk/compileSdk 36 |
| Уведомления | через бесплатное приложение [ntfy](https://ntfy.sh) (раздел 0.5); Firebase и Google-аккаунт не нужны |
| QR-сканер | `@capacitor/barcode-scanner` (нужна камера) |
| Вход | почта + пароль или ключ `OWNER-…`; QR с ключом создаётся в кабинете на странице «Телефон и уведомления» |
| Какие данные уходят в облако | почта и имя владельца, адрес темы ntfy, модель телефона |

> Секреты (ключ подписи и пароли к нему) **никогда не кладём в git** и не пересылаем в мессенджерах. Хранилище — менеджер паролей компании + резервная копия на отдельном носителе.

## 0. Быстрый путь: APK на GitHub

Сборку делает GitHub Actions (`.github/workflows/mobile.yml`), компьютер с Android Studio не нужен. Готовый файл `TS-<версия>.apk` появляется в выпуске на GitHub, а страница «Скачать приложение» в кабинете сама показывает кнопку «Скачать для Android».

### 0.1. Один раз: настройки облака
Те же значения, что уже заданы для сайта (`deploy.yml`), — GitHub → репозиторий → **Settings → Secrets and variables → Actions**:
- `SUPABASE_PROJECT_REF` — ID проекта Supabase (из адреса `https://<ID>.supabase.co`);
- `SUPABASE_ANON_KEY` — публичный anon-ключ проекта;
- `VAPID_PUBLIC_KEY` — по желанию.

Без первых двух выпуск не соберётся (приложение без адреса облака не сможет войти), пробная сборка — соберётся с предупреждением.

### 0.2. Один раз: ключ подписи (рекомендуем сделать до первого выпуска)
1. На своём компьютере (нужен JDK 21, на Windows: `winget install --id Microsoft.OpenJDK.21 -e`) в папке репозитория:
   ```sh
   npm run android:keystore
   ```
   Скрипт создаёт ключ `ts-release.jks` и файл `github-secrets.txt` в папке `~/.ts-keys/android/` (вне репозитория; другую папку можно указать: `npm run android:keystore -- D:\keys`). Пароли в терминал не выводятся — только в этот файл.
2. GitHub → **Settings → Secrets and variables → Actions → New repository secret** — создать четыре секрета, имена и значения взять из `github-secrets.txt`:
   `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`.
3. `ts-release.jks` и `github-secrets.txt` сохранить в менеджер паролей и на отдельный носитель. **Потеряли ключ — новые версии не встанут поверх старой**: всем владельцам придётся удалить приложение и поставить заново. Ключ меняется только так же — через переустановку у всех.

**Чем отличается APK без ключа.** Если секретов подписи нет, выпуск всё равно собирается, но подписывается временным (отладочным) ключом, который каждый раз новый. Такой APK ставится, но **следующую версию нельзя поставить поверх него** — ни подписанную, ни такую же временную: Android требует, чтобы подпись у обновления совпадала. Владельцу один раз придётся удалить приложение (вход потом ввести заново) и поставить новое. В описании такого выпуска об этом написано. Поэтому ключ лучше завести до первого выпуска — тогда все следующие версии ставятся поверх как обычное обновление.

### 0.3. Выпустить новую версию
Одна команда (версия — три числа, каждая следующая больше предыдущей; второе и третье число — не больше 99):
```sh
git tag mobile-v0.1.1 && git push origin mobile-v0.1.1
```
Или без командной строки: GitHub → **Releases → Draft a new release** → в поле **Choose a tag** вписать `mobile-v0.1.1` → **Create new tag** → снять галочку **Set as the latest release** → **Publish release**. Сборка начнётся сама и добавит в этот выпуск файл приложения.

Через 10–15 минут в **Releases** появится выпуск «TS для Android 0.1.1» с файлом `TS-0.1.1.apk` (и `.sha256` для проверки). Ход сборки — во вкладке **Actions → mobile**. Если сборка упала, выпуск не создаётся; причина — в журнале (например, «Нет настроек облака» или «Заданы не все секреты подписи»). Выпуск Android не становится «последним» (Latest) на GitHub — эта отметка остаётся у приложения для ПК, его автообновление читает её.

Номер сборки для Android (versionCode) считается из версии: `1.2.3` → `10203`. Пробная сборка: **Actions → mobile → Run workflow** — APK будет в разделе **Artifacts** этого запуска, выпуск не создаётся; её версия — из `apps/mobile/package.json` с пометкой `-test.<номер запуска>`.

### 0.4. Как установить на телефон
Открыть страницу выпуска (или «Скачать приложение» в кабинете) на телефоне → скачать `TS-<версия>.apk` → открыть файл → разрешить установку из этого источника → войти почтой и паролем кабинета.

### 0.5. Уведомления: ntfy
Тревоги клуба приходят через бесплатное приложение **ntfy** ([F-Droid](https://f-droid.org/packages/io.heckel.ntfy/) — без Google, [Google Play](https://play.google.com/store/apps/details?id=io.heckel.ntfy), [App Store](https://apps.apple.com/app/ntfy/id1625396347)). В TS: **«Телефон и уведомления» → «Получать уведомления через ntfy»** — кабинет создаёт секретный адрес (тему), кнопка **«Подписаться в ntfy»** открывает приложение ntfy и подписывает его. Дальше облако само отправляет туда тревоги по правилам из той же страницы; нажатие на уведомление открывает клуб в кабинете. Адрес темы — секрет: если он попал не туда, на той же странице «Создать новый адрес».

Почему ntfy, а не опрос облака (Supabase Realtime): уведомление ntfy приходит, даже когда приложение TS закрыто или телефон заблокирован, а Realtime работает только пока приложение открыто — а тревога «свет горит без игры» важна именно тогда, когда владелец в кабинет не смотрит. ntfy бесплатен, не требует ни Firebase, ни Google-аккаунта, ни ключей Google (а Firebase Cloud Messaging требует Google-проект и сервисный ключ, которых у нас нет). Отправка в ntfy уже встроена в облако (Edge Functions Supabase) и в кабинет, так что для запуска ничего настраивать не нужно. Realtime при этом остаётся: пока кабинет открыт, он показывает новые тревоги сразу всплывающим сообщением.

## 2. Android: подпись и сборка релиза

### 2.1. Ключ подписи (один раз)
- [ ] Тот же ключ, что для APK на GitHub (раздел 0.2): `npm run android:keystore` → `~/.ts-keys/android/ts-release.jks`, псевдоним `ts`. Отдельный ключ для магазина не нужен: одна подпись — и APK с GitHub, и версия из Google Play обновляют друг друга.
- [ ] Для локальной сборки создать `apps/mobile/android/keystore.properties` (в `.gitignore`, проверить `git check-ignore`), значения — из `github-secrets.txt`:
  ```properties
  storeFile=/home/<user>/.ts-keys/android/ts-release.jks
  storePassword=...
  keyAlias=ts
  keyPassword=...
  ```
  Вместо файла можно задать переменные `ANDROID_KEYSTORE_FILE`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` (так делает GitHub Actions). Без ключа `build.gradle` подписывает release отладочным ключом и пишет об этом в журнал; Google Play такой файл не примет. Ключ задан не полностью или файла нет — сборка останавливается с ошибкой.
- [ ] При первой загрузке в Play Console включить **Play App Signing** (по умолчанию для новых приложений). Если хотите, чтобы APK с GitHub и версия из Play обновляли друг друга, при настройке выберите «использовать свой ключ» и загрузите `ts-release.jks` (Play покажет инструкцию с утилитой `pepk`). Иначе Google подпишет приложение своим ключом, а наш станет ключом загрузки — тогда владельцам, перешедшим с APK на Play, придётся один раз переустановить приложение.
- [ ] Сохранить SHA-1/SHA-256 **ключа подписи приложения** из Play Console → Setup → App signing (пригодятся, если позже понадобятся Google-сервисы, проверяющие подпись).

### 2.2. Сборка `.aab` (каждый релиз)
- [ ] Поднять версию в `apps/mobile/package.json` (`"version": "1.2.0"`) — `build.gradle` берёт оттуда `versionName`, а `versionCode` считает сам (`1.2.0` → `10200`). Play требует новый `versionCode` на каждую загрузку (даже в тестовый трек), поэтому каждая загрузка — новая версия. Можно и без правки файла: `TS_VERSION_NAME=1.2.0 TS_VERSION_CODE=10200`. Версию держим одинаковой с iOS.
- [ ] Собрать: `npm run build:android-release` из `apps/mobile`. Это то же самое, что:
  ```sh
  cd apps/mobile
  npm run build                 # собирает кабинет в www
  npx cap sync android          # копирует www и плагины в android/
  cd android && ./gradlew bundleRelease
  ```
- [ ] Результат: `apps/mobile/android/app/build/outputs/bundle/release/app-release.aab`. Его и загружаем в Play Console (APK магазин для новых приложений не принимает).
- [ ] Проверить подпись: `jarsigner -verify -verbose app-release.aab` → «jar verified», в сертификате `CN=TS`; отпечаток SHA-256 совпадает с тем, что напечатал `npm run android:keystore`.

## 3. iOS: сборка и TestFlight

Нужен **Mac** с актуальным Xcode. С апреля 2026 App Store принимает сборки только с iOS 26 SDK, то есть **Xcode 26+** (Xcode 16 уже не подходит). Нет Mac — облачная сборка: [Codemagic](https://codemagic.io), [Ionic Appflow](https://ionic.io/appflow) или GitHub Actions на `macos-*` раннере (подпись через App Store Connect API key).

- [ ] Платформа уже добавлена (`npx cap add ios` сделан); каждый релиз начинаем с:
  ```sh
  cd apps/mobile && npm run build && npx cap sync ios
  cd ios/App && pod install     # если проект на CocoaPods; на SPM шаг не нужен
  open App.xcworkspace          # (или App.xcodeproj для SPM)
  ```
- [ ] Target **App** → General: Bundle Identifier `kz.ts.owner`, Display Name `TS`, **Version** = `versionName` Android, **Build** — +1 каждую загрузку.
- [ ] Решить про iPad: если в Deployment Info оставлен iPad, Apple потребует скриншоты iPad 13″ и проверит интерфейс на планшете. Проще оставить **только iPhone**.
- [ ] **Signing & Capabilities**: Team — наша организация, «Automatically manage signing». Push Notifications и Background Modes не добавляем: уведомления приходят через приложение ntfy.
- [ ] `ios/App/App/Info.plist`:
  - [ ] `NSCameraUsageDescription` = «Камера нужна, чтобы отсканировать QR-код входа из кабинета TS.» Без этой строки приложение падает при открытии сканера и отклоняется проверкой.
  - [ ] `ITSAppUsesNonExemptEncryption` = `NO` (используем только стандартный HTTPS) — тогда не будет вопроса об экспортном контроле при каждой загрузке.
- [ ] Схема **Release**, устройство «Any iOS Device (arm64)» → **Product → Archive** → Organizer → **Distribute App → App Store Connect → Upload**.
- [ ] В App Store Connect → TestFlight дождаться обработки сборки (10–30 мин), заполнить «What to Test», добавить внутренних тестировщиков (до 100 человек из команды, без проверки Apple). Внешние тестировщики — после короткой бета-проверки.
- [ ] Поставить сборку из TestFlight на реальный iPhone и пройти раздел 5 (уведомления — через ntfy из App Store).

## 4. Материалы для карточек магазинов

### 4.1. Тексты (готовые, можно править)
- [ ] **Название**: `TS` (Google — до 30 символов, Apple — до 30). Если имя занято, вариант: `TS — кабинет владельца`.
- [ ] **Подзаголовок Apple** (до 30): `Клубы под контролем`.
- [ ] **Краткое описание Google** (до 80):
  > Кабинет владельца клубов: выручка, загрузка столов, смены и тревоги.
- [ ] **Полное описание** (Google — до 4000, Apple — то же поле «Description»):
  > TS — приложение для владельцев и управляющих бильярдных клубов и других заведений, которые работают на системе TS.
  >
  > Что можно делать:
  > • смотреть выручку за сегодня, неделю и месяц по каждому клубу и по всей сети;
  > • видеть загрузку столов и залов в реальном времени;
  > • следить за сменами: кто открыл, какая касса, итоги X- и Z-отчётов;
  > • смотреть тарифы и расписание;
  > • получать уведомления о тревогах через бесплатное приложение ntfy: свет горит без игры, игра идёт без света, клуб перешёл на ИБП, связь с клубом пропала, крупный возврат или отмена игры. Нажатие на уведомление открывает нужный клуб;
  > • быстро входить по QR-коду из кабинета, не набирая ключ вручную.
  >
  > Приложение предназначено для действующих клиентов TS. Учётную запись владельца создаёт администратор TS при подключении клуба; регистрации в приложении нет.
- [ ] **Что нового** для первой версии: «Первая версия: кабинет владельца, уведомления о тревогах через ntfy, вход по QR.»

### 4.4. Политика конфиденциальности
- [ ] Опубликовать на нашем сайте по постоянному **HTTPS-адресу** (одинаковый URL в обоих магазинах и в приложении — ссылка на экране входа/настроек). Языки: русский и казахский, по возможности английский для проверяющих.
- [ ] Что в ней должно быть:
  - кто оператор данных (юрлицо, БИН, адрес, почта для обращений);
  - какие данные собираем: почта и имя владельца, хеш пароля / ключ входа, адрес темы ntfy, модель телефона, данные клубов (выручка, смены, тревоги), которые владелец и так ведёт в TS;
  - зачем: вход, показ данных клубов, отправка уведомлений о тревогах;
  - где хранятся: на серверах в Республике Казахстан (закон РК «О персональных данных и их защите»);
  - кому передаются: сервер ntfy (ntfy.sh или свой сервер) — только текст уведомления и адрес темы, для доставки; больше никому, не продаём, рекламы и аналитики нет;
  - сколько храним: пока действует учётная запись; адрес темы ntfy удаляется вместе с устройством в кабинете;
  - права пользователя: доступ, исправление, удаление, отзыв согласия; как удалить учётную запись (раздел 6.3);
  - защита: HTTPS, доступ по ролям;
  - дети: приложение не предназначено для лиц младше 18 лет;
  - дата редакции и как сообщаем об изменениях.

### 4.5. Data safety (Google) — ответы
- [ ] «Собирает или передаёт ли приложение данные?» — **Да**.
- [ ] «Все данные шифруются при передаче?» — **Да** (только HTTPS).
- [ ] «Можно запросить удаление данных?» — **Да**, + URL страницы удаления (Google требует его для приложений с учётными записями).
- [ ] Типы данных (все — **собираются**, **не передаются третьим лицам** в смысле Google: доставка уведомлений через ntfy считается обработкой поставщиком услуг; **обязательны**; цель — **App functionality** и **Account management**):
  - Personal info → **Name**, **Email address**;
  - Device or other IDs → модель телефона (для осторожности);
  - Financial info → **не выбираем**: выручка клубов — данные бизнеса, а не платёжные данные пользователя. Если проверка спросит — пояснить так же.
- [ ] Location, Contacts, Photos, Analytics, Advertising ID — **не собираем**. Проверить объединённый манифест (`android/app/build/intermediates/merged_manifests/…`), что нет `com.google.android.gms.permission.AD_ID`; в Play Console → App content → Advertising ID ответить «Нет».

### 4.6. App Privacy (Apple) — ответы
- [ ] Data Types: **Contact Info → Name, Email Address**. Модель устройства Apple отдельно не спрашивает — не указываем как отдельный тип.
- [ ] Для каждого: Purpose — **App Functionality**; Linked to the user — **Yes**; Used for tracking — **No**.
- [ ] Tracking (ATT) — **не используем**, `NSUserTrackingUsageDescription` не добавляем.
- [ ] Privacy Policy URL — из 4.4.

### 4.7. Возрастной рейтинг
- [ ] Google: анкета IARC — категория «Утилиты/производительность», на все вопросы о насилии, азартных играх, алкоголе, общении пользователей — **Нет** → ожидаемо «3+ / Для всех».
- [ ] Apple: анкета Age Rating — всё **None/No** → **4+**. Азартных игр нет: бильярд в приложении — это учёт времени столов, а не игра на деньги.
- [ ] Google: Target audience — **18+** (бизнес-приложение), «Привлекает ли детей» — Нет.

### 4.8. Тестовый вход для проверяющих
- [ ] Облако, к которому ходит релизная сборка, **доступно из интернета по HTTPS** (проверяющие Apple в США, Google — из разных стран; не закрывать файрволом по стране).
- [ ] Завести **демо-владельца** на стенде/в проде: отдельная почта (например `review@…`), пароль, 1–2 демо-клуба с правдоподобной выручкой, сменами и хотя бы одной тревогой. Никаких реальных клиентских данных.
- [ ] Дополнительно — постоянный ключ `OWNER-…` этого демо-владельца (на случай, если проверяющий захочет войти по ключу). QR проверяющий отсканировать не сможет — в пояснении это написать.
- [ ] Google: App content → **App access** → «Весь функционал или его часть ограничен» → логин, пароль, инструкция.
- [ ] Apple: App Review Information → Sign-in required → логин/пароль; в **Notes**:
  > TS is a B2B app for owners of billiard clubs that already use the TS system. Accounts are created by our administrator when a club is connected; there is no sign-up in the app. Demo account: see above. To trigger a demo alert push, … (описать, как вызвать тестовую тревогу или приложить видео). QR login: the QR code is shown in the TS web cabinet; you can use the key below instead.
- [ ] Не менять пароль демо-владельца и не удалять демо-клубы, пока идёт проверка (и вообще — при каждом обновлении проверяют заново).

### 4.9. Разрешения и обоснование
| Разрешение | Платформа | Зачем | Когда спрашиваем |
|---|---|---|---|
| `CAMERA` | Android | сканировать QR входа | только при нажатии «Войти по QR» |
| `NSCameraUsageDescription` | iOS | то же | то же |
| `INTERNET` | Android | связь с облаком | системное, не спрашивается |

- [ ] Других разрешений в объединённом манифесте нет (проверить после `bundleRelease`); лишнее — удалить через `tools:node="remove"`. Разрешения на уведомления у TS нет — его спрашивает приложение ntfy.
- [ ] Отказ в доступе к камере не ломает приложение: остаётся вход по почте и ключу.

## 5. Перед каждой отправкой в магазин

Прогон на **реальных** устройствах: один Android (лучше 13+ и один старый, 7–9) и один iPhone, сборка из релизного `.aab` (через внутреннее тестирование Play) и из TestFlight.

- [ ] Версия увеличена: Android `versionCode` +1, iOS Build +1, `versionName`/Version совпадают и отличаются от прошлого релиза.
- [ ] Адрес облака в сборке — **HTTPS** продакшена (не `localhost`, не IP стенда).
- [ ] В release нет cleartext: `android:usesCleartextTraffic` не `true`, в `capacitor.config` нет `server.url` и `cleartext: true`; на iOS нет `NSAllowsArbitraryLoads`.
- [ ] Вход по почте и паролю работает; неверный пароль — понятная ошибка.
- [ ] Вход по QR: в кабинете на ПК «Телефон и уведомления» → QR → скан телефоном → вход без ввода ключа. Отказ в доступе к камере → понятное сообщение.
- [ ] Вход по ключу `OWNER-…` вручную.
- [ ] Уведомления доходят: «Получать уведомления через ntfy» → «Подписаться в ntfy» открывает ntfy, устройство «… (ntfy)» появилось в списке; «Отправить тестовое уведомление» и тестовая тревога в демо-клубе приходят при **закрытом** TS.
- [ ] Нажатие на уведомление открывает **нужный клуб** в кабинете.
- [ ] Настройка «какие тревоги присылать» действует: выключенный тип не приходит.
- [ ] Удаление устройства «… (ntfy)» в кабинете останавливает уведомления на этот телефон.
- [ ] Без сети: при запуске виден **офлайн-баннер**, приложение не белый экран; сеть вернулась — данные обновились.
- [ ] Повторный запуск после перезагрузки телефона: сессия сохранилась, вход не нужен.
- [ ] Иконка, имя «TS» и заставка правильные; нет отладочных надписей и тестовых данных.
- [ ] В кабинете у устройств нет «Последняя ошибка» (например, `ntfy 429` — превышен лимит ntfy.sh).
- [ ] Обновлены тексты «Что нового» и, если менялся интерфейс, скриншоты.

## 6. Проверка в магазинах

### 6.1. Google Play
- [ ] Порядок: Internal testing (сразу, без проверки) → Closed testing → Production.
- [ ] **Новый личный аккаунт** (создан после ноября 2023): перед первым выпуском в Production обязателен **закрытый тест не менее чем с 12 тестировщиками, которые 14 дней подряд остаются в тесте**, затем заявка на доступ к Production. Для **аккаунта организации** это требование **не действует**.
- [ ] Сроки: первая проверка нового аккаунта — **до 7 дней**, дальше обычно от нескольких часов до 1–3 дней. Закладываем неделю на первый выпуск.
- [ ] Перед отправкой Play Console → **Publishing overview**: все пункты App content (политика, App access, Ads, Data safety, рейтинг, Target audience, Government apps — «Нет», Financial features — «Нет») зелёные.
- [ ] Выпуск в Production — сначала **staged rollout** 20 % → через 1–2 дня 100 %, если в Android vitals нет сбоев.

### 6.2. App Store
- [ ] Сроки: обычно **1–2 дня**; при замечании — ответ в Resolution Center и повтор, ещё 1–2 дня.
- [ ] Частые причины отказа и как отвечаем:
  - **4.2 Minimum Functionality** («это просто сайт в обёртке»). Ответ: приложение даёт то, чего нет в браузере — **вход по QR через камеру**, хранение сессии на устройстве, работа интерфейса без загрузки с сервера (встроен в сборку, офлайн-баннер). Уведомления идут через ntfy, поэтому аргумент «свои push» здесь не работает — риск отказа выше, чем для Android; в Notes приложить короткое видео с QR-входом.
  - **5.1.1 Data Collection / вход обязателен**. Ответ: это B2B-приложение для существующих клиентов; учётную запись владельца создаёт администратор TS при подключении клуба, регистрации в приложении нет; для проверки выдан демо-доступ (4.8). Не требовать в приложении лишних данных, кроме входа.
  - **5.1.1(v) Удаление учётной записи**. Строго обязательно, если учётную запись можно создать в приложении; у нас нельзя, но проверяющие всё равно часто спрашивают. Решение: в приложении в настройках пункт **«Удалить учётную запись»**, который открывает запрос на удаление (форма на сайте / письмо в поддержку с указанием почты) и объясняет срок исполнения; то же — страница в кабинете. Этот же URL указываем в Google Data safety.
  - **2.1 App Completeness** — демо-вход не работает или облако недоступно. Перед отправкой самим войти под демо-владельцем с мобильного интернета.
  - **5.1.1 / Info.plist** — нет или слишком общий текст `NSCameraUsageDescription`.
  - **2.3 Metadata** — скриншоты не из приложения или с макетами устройства, не совпадающими с реальным экраном.
- [ ] После одобрения выбрать «Manually release» или «Automatically release»; для первого выпуска — вручную, после финального прогона раздела 5 на сборке из TestFlight.

## 7. Обновления

- [ ] **Без магазина менять нельзя ничего в интерфейсе.** В нашей реализации кабинет `apps/cloud-web` **встроен в сборку** приложения (папка `www` внутри `.aab`/`.ipa`), а не грузится с облака. Любая правка интерфейса кабинета, которую должны увидеть пользователи приложения, = **новая версия** в обоих магазинах (раздел 2.2, 3, 5).
- [ ] Без магазина меняется только то, что живёт на сервере: данные, правила тревог, тексты уведомлений, которые формирует облако, API облака (при условии обратной совместимости — старые версии приложения у владельцев остаются месяцами).
- [ ] Это **отличается** от предположения в [APP_PLAN_RU.md](APP_PLAN_RU.md) («мелкие правки интерфейса можно доставлять без магазина, интерфейс грузится с облака»). Почему выбрали встроенный интерфейс:
  - **офлайн-запуск**: приложение открывается и показывает офлайн-баннер без сети, а не пустой экран;
  - **проверка Apple 4.2**: приложение, которое просто открывает удалённый сайт, отклоняют чаще; встроенный интерфейс + QR-вход через камеру — аргумент в нашу пользу;
  - предсказуемость: версия интерфейса всегда совпадает с версией нативных плагинов, а проверенная магазином сборка — с тем, что реально у пользователя.
- [ ] Следствие для облака: API должно поддерживать **как минимум предыдущую версию** приложения. Ломающие изменения — только с проверкой версии приложения и экраном «Обновите приложение».
- [ ] Ритм: копить правки интерфейса и выпускать раз в 2–4 недели; срочные исправления — отдельным релизом (Apple позволяет запросить ускоренную проверку: <https://developer.apple.com/contact/app-store/?topic=expedite>).
- [ ] Каждое обновление проходит раздел 5 целиком и повышает `versionCode` / Build.
- [ ] Раз в год: targetSdk Android под новое требование Google (обычно к августу), Xcode/iOS SDK под требование Apple (обычно к апрелю), продление Apple Developer Program.
