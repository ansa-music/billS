# План: приложение из браузера (PWA) и установка на устройства

Цель: сотрудник открывает адрес HUB в браузере планшета или ПК кассира, нажимает «Установить» — и дальше работает с иконки, на весь экран, без адресной строки, с кэшем на случай обрыва Wi-Fi. Никаких магазинов приложений и установщиков: приложение раздаёт сам HUB клуба.

## Статус

Этапы A, B, D, E и заголовки из C сделаны в ветке `claude/pwa-d4482d`, проверены в браузере на собранном `dist` через HUB (конфигурация `pwa-check`). Инструкция для персонала — в README, раздел «Установка на планшет и ПК (PWA)». Не сделано: HTTPS с локальным CA и имя `hub.local` (C.1, C.2 — отдельный шаг).

Что проверено: манифест отдаётся как `application/manifest+json`, `navigator.serviceWorker.getRegistrations()` возвращает одну активную регистрацию со scope `/`, страница контролируется воркером с первой загрузки, консоль без ошибок, `/api/events` (SSE) и `/api/state` идут через воркер как обычные запросы. Баннер установки (по синтетическому `beforeinstallprompt`): [img/pwa-install-banner.jpg](img/pwa-install-banner.jpg), «Позже» запоминается. Обновление: правка `sw.js` → воркер в ожидании → баннер «Доступна новая версия» → «Обновить» → перезагрузка, вход сохранён.

Решения по ходу: `clientsClaim: true` при `skipWaiting: false` — первый воркер берёт под контроль страницу, которая его зарегистрировала (иначе следующая сборка активируется молча и баннеру нечего переключать), каждая следующая сборка ждёт нажатия; раз в час воркер сам спрашивает HUB о новой сборке (планшет открыт сутками). Иконки рисует `scripts/icons.mjs` чистым JS (PNG через `node:zlib`, без зависимостей и сети), результат закоммичен. В Lighthouse 12+ нет категории «PWA», установимость смотрят в DevTools → Application → Manifest; `npm run audit:pwa` гоняет Lighthouse через `npx @lhci/cli` без тяжёлых зависимостей в репозитории.

## Как это выглядит для клуба

1. Управляющий открывает на планшете `http://hub.local` (или IP мини-ПК, например `http://192.168.1.10`).
2. Вводит ключ доступа → экран зала.
3. Браузер предлагает «Добавить на главный экран» / «Установить приложение». В Chrome на Android — баннер снизу, в Safari на iPad — «Поделиться → На экран „Домой“», в Chrome на Windows — иконка «Установить» в адресной строке.
4. На рабочем столе появляется иконка «TS». Запуск — сразу в полноэкранном режиме, экран не гаснет.
5. Пропал Wi-Fi: приложение открывается из кэша, показывает «Нет связи с HUB», кнопки возвращаются, как только связь вернётся. Данные никуда не теряются — они в HUB.
6. Обновили HUB: при следующем открытии приложение само подтягивает новую версию и показывает «Доступна новая версия — обновить».

## Что сделать в коде (`apps/web` + `apps/hub`)

### Этап A. Манифест и иконки — ✅ готово
- [x] `apps/web/public/manifest.webmanifest`: `name` / `short_name` «TS», `start_url: "/#/"`, `display: "standalone"`, `orientation: "any"`, `theme_color`/`background_color` из токенов, `lang: "ru"`, `scope: "/"`.
- [x] Иконки 192/512 px (maskable) + `apple-touch-icon` 180 px + `icon.svg`: буквы «TS» на зелёном (`scripts/icons.mjs`, `npm run icons`, без внешних сервисов).
- [x] В `index.html`: `<link rel="manifest">`, `<meta name="apple-mobile-web-app-capable">`, `apple-mobile-web-app-status-bar-style`, `theme-color`; viewport без масштабирования.
- [x] Отдельные ярлыки в манифесте (`shortcuts`): «Зал», «Счета», «Сводка».

### Этап B. Service worker — ✅ готово
- [x] `vite-plugin-pwa` (Workbox) в `vite.config.ts`: `precache` для сборки (`index.html`, js, css, шрифт, иконки, манифест) и `NetworkOnly` для `/api/*` — данные всегда с HUB, никакого кэша команд.
- [x] `registerType: "prompt"`: новая версия → баннер «Обновить» в оболочке (`src/pwa.tsx`, под верхней панелью), по нажатию `skipWaiting` + перезагрузка. Без принудительных обновлений посреди смены.
- [x] Офлайн-страница не нужна: оболочка уже показывает «Нет связи с HUB» (`OfflineBanner`).
- [x] `/api/events` (SSE) и `/api/dev/*` не кэшируются (всё `/api/*` — `NetworkOnly`). В dev-режиме воркер не регистрируется.

### Этап C. Раздача с HUB — ✅ заголовки, ⏳ HTTPS и hub.local
- [x] HUB отдаёт `apps/web/dist` на `/` (`@fastify/static`). Заголовки: `manifest.webmanifest` → `application/manifest+json`, `sw.js`, `workbox-*.js`, `index.html` и иконки → `Cache-Control: no-cache`, `assets/*` — год (`apps/hub/src/http/static.ts`, тест `apps/hub/test/static.test.ts`).
- Service worker требует «безопасный контекст»: `http://<ip>` в локальной сети **не считается** безопасным в Chrome (только `localhost`). Решение для клуба — одно из:
  1. [ ] **HTTPS на HUB с локальным CA** (рекомендуется): HUB при установке генерирует свой корневой сертификат (`deploy/linux/install.sh` → `bills ca init`), сертификат ставится на планшеты один раз (QR-код со страницы «Оборудование»), HUB слушает `https://hub.local:443`. Полный PWA, wake lock, камера для QR.
  2. [x] **HTTP как есть** (описано в README): iPad Safari ставит на экран «Домой» без ограничений; Chrome на Android и Windows — только после флага `chrome://flags/#unsafely-treat-insecure-origin-as-secure` с адресом HUB на каждом устройстве (тогда и service worker, и баннер установки работают). Без флага страница работает как обычно, просто без установки. [ ] mDNS-имя `hub.local` на мини-ПК (avahi в `deploy/linux`) — чтобы адрес не зависел от IP.
  3. [ ] **Tailscale/внутренний домен с Let's Encrypt** — для сети клубов с облаком (этап 6): `club1.<домен>` с настоящим сертификатом, DNS указывает на локальный IP.
- Для пилота: вариант 2 сразу, вариант 1 — в `deploy/` одной командой.

### Этап D. Поведение «как приложение» — ✅ готово
- [x] Полноэкранный режим и wake lock уже есть (`kiosk.ts`); в standalone-режиме (`display-mode: standalone` или `navigator.standalone` на iPad) кнопка «На весь экран» не показывается.
- [x] Запрет масштабирования пальцами (`viewport maximum-scale=1, user-scalable=no`), `overscroll-behavior: none`, `touch-action: manipulation`, в установленном приложении `user-select: none` (кроме полей ввода).
- [x] Вход по ключу: токен живёт на HUB и хранится в `localStorage` приложения; название устройства (`bills.device`) запоминается и подставляется при следующем входе; у установленного приложения своё хранилище, поэтому после установки ключ вводится один раз заново.
- [x] Баннер «Установите приложение» (событие `beforeinstallprompt`) с кнопками «Установить» / «Позже» — показывается, пока не установлено; «Позже» запоминается на устройстве (`localStorage`, `bills.pwa.install`). Для iPad / iPhone в Safari — подсказка «Поделиться → На экран „Домой“» (по userAgent и `navigator.standalone`), закрывается один раз.

### Этап E. Проверка — ✅ готово
- [x] `npm run audit:pwa` — Lighthouse на собранном dist через `npx @lhci/cli` (нужен установленный Chrome; в зависимости репозитория не добавлен). Категории «PWA» в Lighthouse 12+ больше нет, порог ≥ 90 не к чему применять — установимость проверяется в DevTools → Application → Manifest.
- [x] Ручной прогон в браузере на `http://localhost:4800/` (HUB с `dist`, см. «Статус»): установка (баннер), обновление версии, SSE через воркер. [ ] На реальных устройствах — Android Chrome (планшет), iPad Safari, Windows Chrome/Edge (касса): установка, запуск с иконки, обрыв Wi-Fi, обновление версии — после развёртывания в клубе.
- [x] Тест: HUB отдаёт манифест и `sw.js` с нужными заголовками (`node --test`, `apps/hub/test/static.test.ts`).

## Что НЕ входит
- Магазины приложений (Google Play / App Store) — отдельный план через Capacitor, нужен только для кабинета владельца с push-уведомлениями.
- Нативная печать чеков — в PWA печать идёт через системный диалог браузера (уже сделано, `window.print`); тихая печать без диалога — только в Tauri/Electron-обёртке для ПК кассира (отдельный этап).
