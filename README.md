# BILLIARD CONTROL (billS)

Система управления сетью бильярдных клубов: открытие и закрытие времени на столе с физическим включением лампы, тарифы, официанты, кассовые смены, график сотрудников. Владелец компании с несколькими клубами видит и контролирует все филиалы из одного кабинета.

> **Для следующих сессий (людей и ИИ-агентов):** сначала прочитай раздел [«Как продолжать работу»](#как-продолжать-работу) и [«Текущий статус»](#текущий-статус). План ниже — источник правды; после каждого этапа обновляй статус здесь же.

## Как это устроено

```
                 ┌──────────────── ОБЛАКО (этап 6) ─────────────────┐
                 │  Кабинет владельца: все клубы, отчёты, тарифы,   │
                 │  сотрудники, права. Компания → клубы → столы.    │
                 └───────────────▲──────────────────────────────────┘
                                 │ синхронизация (outbox, только исходящие события
                                 │ и входящие настройки; клуб работает без интернета)
┌──────────────────── КЛУБ ──────┴───────────────────────────────────────────┐
│  HUB — мини-ПК в клубе (apps/hub): API, база SQLite, правила, аудит        │
│     ▲                         ▲                          │                 │
│     │ LAN / Wi-Fi             │                          │ команды лампам  │
│  планшеты официантов,     касса (ПК кассира,             ▼                 │
│  экран зала (apps/web)    ККМ, терминал, QR)     контроллер реле (ESP32 / │
│                                                  Modbus) → лампы столов    │
└────────────────────────────────────────────────────────────────────────────┘
```

Главная идея: **в каждом клубе стоит локальный HUB**. Столы, лампы и касса работают через него, даже если пропал интернет. Облако нужно владельцу (сводка по филиалам, отчёты, настройки), но не нужно для того, чтобы открыть стол.

### Роли

| Роль | Где действует | Что может |
|---|---|---|
| Владелец (Owner) | вся компания | все клубы, отчёты, тарифы, сотрудники, права, отмены и возвраты |
| Управляющий (Manager) | свой клуб | тарифы клуба, график, сотрудники клуба, подтверждение возвратов и отмен |
| Кассир (Cashier) | свой клуб, на смене | открывает и закрывает кассовую смену, принимает оплату, открывает и останавливает столы |
| Официант (Waiter) | свои столы на смене | открывает и останавливает свои столы, добавляет заказы из бара |
| Платформа (Super admin) | все компании | наша сторона: подключение компаний, подписка, поддержка |

### Ключевые правила (инварианты)

Эти правила уже закреплены в коде и тестах — не ломай их:

1. **Время считается с момента, когда лампа подтвердила включение**, а не с нажатия кнопки. Если контроллер не ответил — игра не началась, деньги не начисляются.
2. **Время останавливается в момент нажатия «Стоп»**, а не когда лампа подтвердит выключение: гости не платят за задержку оборудования.
3. **На столе может быть только одна живая игра** (`OPENING` или `ACTIVE`). Защита — и в коде, и уникальным индексом в базе.
4. **Каждая команда идемпотентна**: клиент присылает `Idempotency-Key`, повтор того же запроса (обрыв сети, двойное нажатие) возвращает тот же результат и ничего не дублирует.
5. **Тариф фиксируется в игре при открытии** (снимок). Изменение тарифа не меняет цену уже идущих игр.
6. **Деньги — целые числа в минимальных единицах** (тиыны/копейки). Никаких float.
7. **Каждое действие пишется в аудит** (кто, что, когда, данные) и в outbox для будущей синхронизации с облаком.
8. **HUB после перезапуска восстанавливает состояние**: идущие игры продолжают считаться, лампы приводятся к нужному состоянию, незавершённые команды досылаются.
9. **После «Стоп» стол сразу свободен**, а игра превращается в счёт «ожидает оплаты». Неоплаченные счета видны кассиру; с ними нельзя будет закрыть смену (этап 2).

### Нюансы, которые легко упустить

- **Защита от «своих».** Главная причина, по которой клубы покупают такие системы, — персонал включает свет друзьям без оплаты. Поэтому лампа должна питаться **только через реле системы**, выключатели на стене убираются, а датчик тока на линии лампы сообщает, горит ли она на самом деле. Свет без игры → тревога владельцу.
- **Контроллер не должен гасить свет сам**, если пропала связь с HUB или HUB перезагрузился: идёт игра, люди с киями. Реле держит последнее состояние; HUB при старте сверяет и досылает команды.
- **Отключение электричества.** После возврата питания время считается от реального начала игры; HUB должен быть на ИБП, контроллер — восстанавливать состояние после подачи питания.
- **Пропал интернет** — клуб работает полностью: столы, касса, лампы. Облако догоняет из outbox.
- **Тарифы по времени суток и дням недели**, игра через границу тарифа (день → вечер, через полночь) делится на отрезки. Окно «пт 22:00–06:00» относится к пятнице, даже когда уже наступила суббота.
- **Округление и минимум**: шаг тарификации (поминутно, по 5/10/15 мин), минимальное время, бесплатные первые минуты на отмену. Всё задаётся в тарифе, а не в коде.
- **Предоплаченное время** («на 1 час»): автоостановка по таймеру и мигание лампы за 5 минут до конца — гости понимают, что время заканчивается.
- **Перенос игры на другой стол**, продление, объединение и разделение счёта, частичная оплата, смешанная оплата (наличные + карта + Kaspi QR).
- **Отмены и возвраты** — только с причиной и подтверждением управляющего, всё в аудите. Скидки — по правам, с лимитом.
- **Фискализация (Казахстан):** онлайн-ККМ и ОФД — на каждую оплату нужен фискальный чек. Интеграция с ККМ — отдельный этап, требования нужно проверить юридически.
- **Часовой пояс клуба** хранится в настройках клуба (у сети могут быть филиалы в разных поясах).
- **Время HUB** — источник правды для начисления; планшеты могут врать часами, поэтому UI считает время от серверного.
- **Бэкапы** базы HUB каждый день + выгрузка в облако; обновления HUB без потери идущих игр.

## Структура репозитория

```
packages/domain   чистая бизнес-логика без ввода-вывода: тарифы, расчёт стоимости, деньги
apps/hub          локальный сервер клуба: HTTP API, SQLite, лампы, аудит, идемпотентность
apps/web          экраны клуба (React + Vite): зал, заказы, бар, настройки, сотрудники, журнал, кабинет владельца
```

Контракт HTTP между HUB и экранами (типы `HubState`, `SessionView` …) лежит в `packages/domain/src/api.ts` — общий для обеих сторон.

Стек: Node.js 24 (TypeScript запускается напрямую, без сборки), Fastify, встроенный `node:sqlite`, React 19 + Vite. Тесты — встроенный `node --test`.

HUB слушает `http://localhost:4310`, экраны — `http://localhost:5173` (Vite проксирует `/api` на HUB). При первом запуске HUB создаёт демо-клуб с 6 столами, двумя тарифами («Стандарт», «Снукер»), пятью демо-сотрудниками (владелец, управляющий, кассир, официант, платформа; PIN `1234`) и демо-меню бара. Данные лежат в `apps/hub/data/hub.db`; чтобы начать с чистого листа, останови HUB и удали этот файл. Настройки — переменные окружения, см. `.env.example` (файл `.env` в корне подхватывается сам).

На экране зала внизу есть панель **«Симулятор ламп»**: можно отключить контроллер, задать задержку, сломать или «потерять» ответ на следующую команду — так проверяются отказы без железа.

Проверка типов: `npm run typecheck`.

### HTTP API HUB

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/state` | всё для экрана: клуб, тарифы, столы с играми и лампами, неоплаченные игры, тревоги |
| GET | `/api/events` | SSE: событие `changed` при любом изменении — экраны перечитывают `/api/state` |
| POST | `/api/tables/:tableId/open` | открыть стол, тело `{ "tariffId"?: string }` |
| POST | `/api/sessions/:sessionId/stop` | остановить игру (до подтверждения лампы — отмена без оплаты) |
| POST | `/api/alerts/:alertId/resolve` | отметить тревогу принятой |
| GET/POST | `/api/dev/lamps` | симулятор ламп (только пока нет настоящего контроллера) |

Остальные маршруты — по областям, каждая в своём файле `apps/hub/src/http/routes/*.ts`:

| Область | Маршруты | Файл |
|---|---|---|
| Настройки клуба | `GET /api/club`, `POST /api/club`, `POST /api/tables`, `POST /api/tables/:id/update`, `POST /api/tables/reorder`, `POST /api/tariffs`, `POST /api/tariffs/:id/update` | `routes/settings.ts` |
| Бар и заказы | `GET /api/bar/catalog`, `POST /api/bar/categories[/:id/update]`, `POST /api/bar/products[/:id/update]`, `POST /api/sessions/:id/orders`, `GET /api/sessions/:id/orders`, `POST /api/orders/:id/cancel` | `routes/bar.ts` |
| Вход и ключи | `POST /api/auth/login`, `GET /api/auth/me`, `POST /api/auth/logout`, `GET/POST /api/staff/:id/keys`, `POST /api/keys/:id/revoke` | `http/auth.ts` |
| Сотрудники и журнал | `GET /api/staff`, `POST /api/staff[/:id/update]`, `POST /api/staff/:id/verify-pin`, `GET /api/audit?actor=&tableId=&action=&from=&to=&limit=&before=` | `routes/staff.ts` |
| Кабинет владельца | `GET /api/reports/summary?date=YYYY-MM-DD` | `routes/reports.ts` |

Типы запросов и ответов — в `packages/domain/src/api.ts`. Все POST требуют заголовок `Idempotency-Key` (8–200 символов), проходят через `runCommand` (`http/command.ts`) и пишут аудит. Кто действует — сотрудник из токена сессии (`Authorization: Bearer`, см. «Ключи доступа»); заголовок `X-Actor` больше не является источником правды (в тестах HUB собирается с `trustActorHeader`, в проде — никогда).

### Ключи доступа и иерархия

Вход — по **ключу доступа**: секретная строка вида `OWNER-7K3Q-M2PX-9HWD-4RTB` (префикс называет роль, остальное случайно, без похожих символов 0/O/1/I). Ключ показывается один раз при выдаче; HUB хранит только его хэш (`access_keys`). При входе (`POST /api/auth/login`) ключ меняется на токен сессии (30 дней, продлевается при использовании; хранится хэшем в `auth_sessions`), который экраны шлют как `Authorization: Bearer …`. Без токена HUB отвечает `401`, не по роли — `403`. Публичны только `/api/health`, `/api/auth/login`, `/api/events` (SSE без данных) и `/api/dev/*` (симулятор).

Иерархия — кто кого нанимает и кому выдаёт ключи (`ASSIGNABLE_ROLES` в `permissions.ts`):

```
Техподдержка (TECH-…, наша сторона)   → выдаёт ключи владельцу и техподдержке, видит всё
  Владелец (OWNER-…)                  → управляющие, кассиры, официанты, другие владельцы
    Управляющий клуба (MGR-…)         → управляющие, кассиры, официанты своего клуба
      Кассир (CASH-…), официант (WTR-…) → ключи никому не выдают
```

Правила, которые HUB проверяет сам: управлять (нанять, изменить, выдать или отозвать ключ, уволить) можно только сотрудником той роли, которую ты сам вправе назначить; свою роль изменить и себя уволить нельзя; последнего активного владельца убрать нельзя; отзыв ключа сразу гасит все сессии, открытые с него; уволенный сотрудник теряет сессии немедленно. Все события — `auth.login`, `auth.logout`, `key.issued`, `key.revoked` — в аудите, сам ключ в аудит не попадает.

**Первые ключи.** При старте HUB проверяет, что у каждого активного владельца и техподдержки есть рабочий ключ; если нет — выдаёт и записывает в `first-run-keys.txt` рядом с базой (`apps/hub/data/`) и в лог. На свежем демо-клубе ключи получают все пять демо-сотрудников. Файл нужно передать людям и удалить. Дальше ключи выдаются на странице «Сотрудники» → «Ключи» (с меткой «планшет у бара» и сроком действия), там же отзываются.

### Страницы и роли

Приложение `apps/web` — один SPA с хэш-роутером (`src/router.tsx`), общей навигацией (`src/Layout.tsx`) и входом по ключу доступа (`src/Login.tsx`; токен и сотрудник хранятся в `localStorage`, экраны шлют `Authorization: Bearer`). Права — одна таблица «действие → роли» в `packages/domain/src/permissions.ts` (`can(role, action)`): навигация и кнопки прячутся по ней, а HUB проверяет то же самое на каждом маршруте (`guard(action)` для GET, пятый аргумент `runCommand` для POST). Супер-админ платформы (техподдержка) видит всё.

| Страница | Маршрут | Кто видит | Что может |
|---|---|---|---|
| Зал | `#/` | все сотрудники | открыть/остановить стол, выбрать тариф; тревоги принимает кассир и выше |
| Заказы | `#/orders` | официант, кассир, управляющий, владелец | добавить товары из бара к идущей или неоплаченной игре; отменить заказ с причиной — кассир и выше |
| Бар и меню | `#/bar` | управляющий, владелец | категории и товары: название, цена, остаток, активность |
| Настройки клуба | `#/settings` | управляющий, владелец | столы, тарифы (редактор окон с предпросмотром «час сейчас»), экран зала (логотип, тема, размер карточек, что видит официант), правила; название/часовой пояс/валюта — только владелец |
| Сотрудники | `#/staff` | управляющий, владелец | сотрудники, роли (не выше своей), PIN (хранится хэшем), увольнение, закрепление официанта за столами |
| Журнал | `#/audit` | управляющий, владелец | аудит действий с фильтрами по сотруднику, столу, типу действия и датам |
| Кабинет владельца | `#/owner` | владелец, управляющий | выручка за день/неделю/месяц, загрузка столов по часам, средний чек, топ столов, тревоги, быстрые переходы; переключатель клубов — заготовка этапа 6 |
| Платформа | `#/platform` | супер-админ | макет этапа 8: компании-клиенты, их клубы, подписки (данные ненастоящие) |

Настройки экрана зала применяются ко всему приложению через атрибуты на `<html>` (`data-theme`, `data-cards`, `data-hide-amounts`) — см. `src/app.css`. Демо-сотрудники создаются при старте HUB (PIN у всех `1234`, ключи — в `first-run-keys.txt`), демо-меню — тоже.

## Референсы

Готовые SaaS-шаблоны не дают бильярдного ядра (таймеры, лампы, офлайн), поэтому ядро пишем сами, а у шаблонов берём идеи:
- **BoxyHQ SaaS Starter Kit** — модель организаций, ролей и аудита для облачного кабинета (этап 6).
- **ixartz SaaS Boilerplate** — организация интерфейса и тестов (зависит от Clerk — для офлайн-HUB не подходит).
- **ERPNext** — кассовые документы, смены, сверка (этап 2).
- **Twenty CRM** — пример настраиваемых объектов и прав.

Перед использованием чужого кода в коммерческом продукте — проверить лицензию (у Twenty смешанное лицензирование, у части шаблонов лицензия не указана).

## Текущий статус

**Этап 1 почти готов** (см. чек-лист выше), **этапы 3, 4 и 6 начаты** — страницы помимо экрана зала (см. «Страницы и роли»): настройки клуба, бар и заказы, сотрудники и журнал, кабинет владельца, макет платформы. 93 теста (`npm test`: 37 domain + 56 hub), все страницы проверены в браузере от реального HUB на ПК и на телефоне (375 px), в тёмной и светлой теме. Параллельно в другой ветке делается этап 2 (счёт, оплата, смена); при слиянии заказы бара (`bar_orders` по `session_id`) становятся строками чека. Следующие задачи: пауза и перенос игры, вход по PIN с проверкой прав на HUB, фильтр столов официанта по закреплению.

Для двух копий репозитория рядом (например, worktree) есть второй набор портов: `.env.alt` (HUB 4320, web 5180, своя база `hub-alt.db`) и конфигурации `hub-alt` / `web-alt` в `.claude/launch.json`; Vite читает `HUB_PORT` и `WEB_PORT` из окружения.

Принятые решения, которые стоит знать:
- **База клуба — SQLite** (встроенный `node:sqlite`): один файл, без Docker и отдельного сервера, работает на мини-ПК без обслуживания. PostgreSQL — для облака (этап 6).
- **После «Стоп» стол освобождается сразу**, а неоплаченная игра висит у кассира. Альтернатива (держать стол до оплаты) — вопрос к заказчику, см. «Открытые вопросы».
- **Команды лампам — очередь в базе**: пишутся в той же транзакции, что и игра; новая команда для стола отменяет ожидающую; повторы с паузами; при старте HUB всё досылается.
- **Ранняя версия от Codex** (PostgreSQL в Docker) в репозиторий не попала; этот код написан заново и от неё не зависит.

## Как продолжать работу

1. Прочитай этот README целиком, особенно «Ключевые правила».
2. `npm install && npm test` — все тесты должны быть зелёными до начала работы.
3. Возьми первый невыполненный пункт текущего этапа.
4. Бизнес-правила (расчёты, переходы статусов) — в `packages/domain` с тестами; ввод-вывод и база — в `apps/hub`.
5. Новое поведение — сначала тест, особенно для денег, ламп и восстановления.
6. Изменение схемы базы — только новой миграцией в `apps/hub/src/migrations/` (старые не трогать).
7. В конце: отметь пункты в плане, обнови «Текущий статус», закоммить.
